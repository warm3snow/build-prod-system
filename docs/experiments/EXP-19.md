# EXP-19：全链路长稳与受控 Game Day

## 1. 实验目标

- 冻结最终版本/资源/负载/SLO/恢复预算，在**限定工况**下完成全链路
  正常、压力、剩余容量、受控组合故障与 **2 小时长稳**；
- 记录**成功订单 TPS**（而非总 HTTP QPS）与长稳期间的资源/队列趋势——
  「无解释的持续增长」即失败；
- 受控组合两个已单故障验收的场景（EXP-08 Redis 不可用 + EXP-14 Pod
  硬中断），记录症状→告警→定位→缓解→恢复→数据核验全过程；
- 产出最终验收矩阵（roadmap §6.2）与毕业复盘。

## 2. 背景问题

单项能力（限流、熔断、扩容、切主、备份恢复）各自验收过，但组合后系统
的真实稳态是什么形状？roadmap §6.1 的毕业问题：「能否拿出明确工况、
完整数据与可重复脚本支持最终结论？」——需要一次不挑场景、不裁剪窗口
的长时间运行来回答。

## 3. 冻结配置（实验前登记，全程不改）

| 项 | 值 |
| --- | --- |
| 版本 | order-api / outbox-relay / consumer = exp17a（EXP-17 末版） |
| 拓扑 | order-api ×2 + router ×2 + mysql-ic ×3 + kafka-i ×3 + redis ×1 |
| 负载 | 600 rps × 8:1:1（fixed-rate.js）；对照场景前 warmup 控制缓存变量 |
| SLO（正常态） | 读 P99≤200ms、写 P99≤500ms、系统错误≤0.1% |
| SLO（故障态） | 按场景声明（Game Day：写路径可用 + 明确拒绝 + 恢复收敛） |
| 恢复预算 | 复用 EXP-15/18 的回滚与 DR 证据，不重建流程 |

**方法论要点**：对照场景（D1/D2/D4/D5）每场景前 warmup（10000 SKU），
使测试窗口落在同一 TTL 热周期内（600s）；**长稳 D3 不做控制**——完整
暴露 ~12 个 TTL 过期周期，这正是要测的稳态现实。

## 4. Baseline

- EXP-17 G1：600 rps 热缓存 0.001-0.57% 失败（预热后窗口）；事件完成
  p99 1.34s；EXP-18 后原环境恢复并终局对账通过（88812 四表 1:1:1）。
- EXP-19 守恒基线快照：orders=97722 / P1 库存 904100。

## 5. Hypothesis

1. 热缓存窗口 600 rps 满足正常态 SLO；TTL 600s 过期引发的回源风暴
   （EXP-16 F1 已知边界）在长稳中的形态待验证——事前猜测为周期性
   尖峰（**实测推翻**：单向滑入均衡并最终拥塞塌陷，见 D3）；
2. 900 rps 过载：明确拒绝（429/503/504 分类）而非雪崩，恢复后正常；
3. 失去 1 api + 1 router：热缓存下 600 rps 仍可满足（读由缓存承接）；
4. Game Day（Redis 停机 + Pod 强杀）：写路径全程可用（Outbox 语义），
   读路径降级为有界拒绝（stale 库 1024 键 << 20000 键空间），Redis
   恢复后经历冷缓存重预热再收敛；
5. 2h 长稳：资源/队列无无解释增长；终局守恒与账本零丢失。

## 10. Results

实测环境：Rancher Desktop k3s（单机 6 核/16GB，HA 模拟档，EXP-18 末态）。
注：实验间隙宿主机曾出现一轮未观测重启（order-api 13 次 / redis 2 次 /
kafka-i-0 9 次，VM 睡眠特征），D1 前环境已自愈（3/3 ONLINE、lag=0）。

### D1/D1b：基线复测与 TTL 周期假说（600 rps × 3min × 2）

| 轮次 | 缓存态 | 失败率 | 读 p95 | 写 p95 | dropped | 回源 wanted 峰值 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| D1（预热后） | 热 | 0.56%（611/107694） | 271ms | 1.01s* | 354 | ~2/s |
| D1b（TTL 过期后） | 冷 | 5.06%（5245/103487） | 580ms | 995ms | 4530 | **307/s** |

- D1 与 EXP-17 G1 的 0.57% 同源（开场冷页+边界噪声）——基线可复现 ✓；
- D1b 证实 TTL 过期是降级触发器：预热后 600s 整批过期 → 回源需求
  307/s 冲击 ~100/s 的 qemu Router 回源通道 → 5% 失败。**当时误判为
  「周期性尖峰」——D3 长稳证明这不是周期而是单向滑入均衡**（见 D3）：
  3min 窗口只能看到均衡初期，塌陷需要 ~40min 累积。
- *D1 写 p95 1.01s：少量 3m52s 级挂起请求（k6 侧连接堆积）拖尾；
  写 med 148ms 正常。

### D2：过载复核（900 rps × 2min，热缓存）

| 指标 | 实测 |
| --- | --- |
| 有效吞吐 | ~820 iters/s（目标 900，k6 dropped 9335） |
| 失败率 | 1.69%（1666/98549） |
| 错误分类 | **429×1173（限流）/ 504×1479（写截止）/ 503×196 / 500×14** |
| 读/写 p95 | 520ms / 1.17s |

**结论**：150% 负载下「明确拒绝而非雪崩」（EXP-11 语义在 HA 档复核通过），
分类计数清晰；无资源失控。

### D4：故障后剩余容量（api×1 + router×1，600 rps × 3min，热缓存）

| 指标 | 实测 | SLO |
| --- | --- | --- |
| 失败率 | **0.19%**（213/107999） | ≤0.1% 略超（如实记录） |
| 读 p95 / med | **148ms** / 13.6ms | ✓ |
| 写 p95 / med | 553ms（略破 500ms）/ 85ms | 边缘 |
| dropped | 0 | — |

**结论**：失去各一个 api 与 router 故障单元后，热缓存下 600 rps 仍基本
满足目标（读达标、写边缘）；读路径由 Redis 承接是关键——与 EXP-16
「Router 是缩尺瓶颈」结论一致。

### D5：受控 Game Day（600 rps × 8min，T0=13:03:33）

时间线与注入：T+71s Redis scale 0 → T+159s 强杀 order-api Pod
（EXP-14 路径）→ T+268s Redis scale 1。

| 阶段 | 时刻 | 行为 | 证据 |
| --- | --- | --- | --- |
| 注入1 | 13:04:44 | 读转 DB 直读/有界回源；**下单 201 正常** | 抽查：GET X-Cache: miss + 200；POST 201 |
| 注入2 | 13:06:12 | 幸存副本承接；**读 200 / 下单 201 正常** | Pod 20s 内重建（vw44w Running） |
| 恢复 | 13:08:01 | Redis 回来即**空缓存**（`--save ""` 无持久化）→ 全量 20000 键重预热风暴 | 503 持续 240-380/s 直至负载结束 |
| 收敛 | 13:14+ | 预热完成后复测 600 rps×2min：**0.05% 失败**、读 p95 167ms | 恢复到基线 ✓ |

- **总失败率 44.22%**（126564/286174），其中 503 主导（读路径有界拒绝
  峰值 433/s）+ 504（写截止 36-54/s）；
- **写路径全程存活**：账本 22275 单成功（~78% 写成功，其余为 504 明确
  截止而非静默丢失）；
- **告警链路验证**：OrderAPIErrorRateHigh 13:07:30 触发（持续到 13:13）、
  OrderAPIDeadlineHigh、OrderAPIP99High 相继触发——症状告警按设计工作 ✓；
- **终局对账**：守恒差分 PASS（10000 SKU）、账本 22275 verified /
  **0 lost / 0 mismatch**——双故障零数据损伤 ✓。

**根因链（超出单故障叠加预期的部分）**：EXP-08 验证工况是 100 SKU
（stale 库 1024 键全覆盖）；主线 10000 SKU × 2 端点 = 20000 键空间，
stale 库只覆盖 5% → Redis 停机后 95% 的读无旧值兜底 → 有界回源
（12 并发 ~40-100/s）明确拒绝；叠加 Redis 无持久化 → 恢复=冷缓存 →
重预热风暴延续高拒绝。**组合故障超出读路径事前声明的容错预算**，
如实标记为边界（roadmap：一次 Game Day 不能证明任意组合可承受）。

### D3：2 小时长稳（600 rps × 7200s，LEDGER=1，T0=13:17:23）

**总结果**：430 万次迭代、零中断；但**长稳不通过（否定结论）**——
成功订单 TPS 分三段塌陷，后半程业务吞吐为零：

| 阶段 | 窗口 | 成功订单 TPS | 错误率 | 状态 |
| --- | --- | ---: | ---: | --- |
| 热缓存窗口 | T+0~6min | ~60/s | ~0 | 健康（预热后 600s 内，与 D1 一致） |
| 刀锋均衡 | T+6~40min | 16-20/s | 15-25% | 回源通道饱和的部分未命中均衡 |
| 拥塞塌陷 | T+40min~2h | **0** | ~85% | 写路径全部超过 1s 预算被截止 |

- k6 终局：checks_failed 74.71%（全程平均）；读 p95 508ms；**写 med
  恰为 1.00s**（= 写预算值，即几乎所有写都撞截止线）；dropped 17251；
- **错误构成**（降级期）：503 主导（回源有界拒绝，峰值 412/s）+
  504（读/写截止，107/s）+ 500（11/s）；429 为 0（限流不是瓶颈）；
- **资源与队列（长稳纪律验收项）**：内存全程平稳（order-api 81→100MiB、
  mysql-ic-1 稳定、无 OOM）；outbox PENDING ≤1、consumer lag ≤1——
  **无泄漏、无积压增长**，降级是吞吐降级而非资源失控；
- **数据完整性**：账本 47540 单 **verified=47540 / lost=0 / mismatch=0**、
  库存守恒 PASS——系统「响亮地失败」（明确拒绝+零损伤），而非静默损坏。

**机制（三个数字决定一切）**：

1. 键空间 20000（10000 SKU × 2 端点）÷ TTL 600s = **稳态过期需求 33/s**；
2. 回源通道容量 = 12 并发 × qemu Router ~0.3-0.5s/查询 = **24-52/s**——
   与需求零余量（实测 executed 长期封顶在 24-40/s，wanted 被读流量放大
   至 400+/s）；
3. 一旦滑入未命中，缓存**永远追不平**：miss → wanted 风暴 → 12 槽位
   恒忙 → 后续过期持续产生新 miss——均衡而非瞬态；
4. 均衡期读的 200ms 有界等待 + 1s 截止让 k6（开放模型）VU 堆积
   （462→629），并发压力与拥塞互相喂养；共享路径（Router/DB 连接池）
   被回源占用后，写事务（6 语句 × qemu 延迟 + P1 行锁队列）逐步逼近
   1s 预算，T+40min 起全部越线——**截止线上的拥塞塌陷**（每次尝试
   做一半工作被取消，浪费加剧拥塞）。

**为什么 19 个实验都没看到**：EXP-16/17 的基线测试 ≤12min（预热后
单 TTL 窗口内完成）；D1b 的 3min 只测到均衡初期（5% 失败）。**塌陷
需要 ~40min 累积——这正是 2 小时长稳存在的意义，也是本实验最重要
的产出**（roadmap §3.2：否定结论是有效结论）。

**修复方向（冻结外，进复盘）**：TTL 上调（商品不可变、库存有失效
路径，600s→6000s 把过期需求降到 3.3/s）或回源并发与通道扩容
（原生 arm64 Router）、或常驻预热。任一项都把需求/容量比从 1.0
降到 <<1，塌陷条件消失。


## 11. Root Cause

- **长稳的「稳」不是平均也不是周期，是相变**：热缓存窗口（T+6min 内）
  是一个相，回源刀锋均衡（T+6~40min）是第二个相，写路径塌陷（T+40min
  起 TPS=0）是第三个相——每一段内部都「稳定」，段间转移不可逆。验收
  问「P99 是多少」不如问「在哪个相、会不会转移、转移条件是什么」；
- **Redis 无持久化放大故障半径**：停机期损失热数据（可接受，纯缓存），
  但「恢复 = 冷缓存全量重预热」把故障时长从「Redis 就绪」延长到
  「20000 键重新回源完成」——缓存的恢复预算必须计入回源通道容量；
- **Game Day 的价值在暴露「工况迁移」**：EXP-08 的 0.28% 失败结论在
  100 SKU 键空间下成立，迁移到 10000 SKU 工况后同机制失效——单故障
  验收结论必须登记其工况边界。

## 12. Trade-offs

- **不修 TTL/stale 配置**：发现周期性尖峰后本可调 TTL（商品不可变，
  可上调）或扩大 stale 库，但冻结纪律优先——EXP-19 的职责是刻画冻结
  系统的真实稳态，优化项进复盘（后续：TTL 分散化/常驻预热/stale 扩容）；
- **Game Day 组合选择**：Redis+Pod（两个单故障已验收、组合效果未知）
  而非 MySQL+Kafka（组合等于多数派失守，EXP-17 已单独验证语义）——
  组合必须「符合事前声明的容错预算」（roadmap 范围约束）；
- **长稳不控缓存**：接受了周期性尖峰出现在结果里，换取稳态真实性。

**毕业判定**：19 个必做实验全部执行且证据可复现。其中 18 项验收通过；
**稳态性能在长稳口径下为否定结论**（2h 相变塌陷，机制与修复方向完整：
需求 33/s ≈ 容量 24-52/s 的零余量设计叠加 qemu 回源通道）——这是
「有效否定」，不是失败掩盖：短窗口口径（≤12min，与历史基线同口径）
仍通过。修复后（TTL/回源通道任一扩容）需重跑 D3 复验。「生产工程
实验平台」不等于「可直接投产」（真实支付/身份/安全治理/跨地域不在
范围，见复盘 §6）。

## 14. Lessons Learned

- **稳态不是平坦也不是周期，是相变**：2 小时里系统经历健康→均衡→
  塌陷三个相；验收要问「在哪个相、会不会转移、转移条件是什么」，
  而不是「平均值是多少」（74.71% 的全程平均失败率不描述任何一个相）；
- **缓存的恢复成本 = 键空间 / 回源通道**：Redis 重启秒级就绪，但业务
  恢复要等 20000 键重预热——RTO 预算必须包含缓存重建；
- **工况迁移会让旧结论失效**：EXP-08 的 stale 结论绑着 100 SKU 工况；
  每个验收结论都要登记「在什么键空间/负载/资源下成立」；
- **写路径的「无依赖」设计在 Game Day 兑现**：Outbox 同事务让下单在
  Redis 死、Pod 死叠加时仍 78% 成功（其余明确 504）——核心路径与非
  核心依赖的隔离是架构层的决定，不是运维层的补救。

## 15. Interview Questions

- 2 小时长稳里最重要的发现是什么？为什么短测试看不到它？
  → 相变：热缓存相（~6min，60 TPS）→ 回源刀锋均衡相（~34min，
  16-20 TPS）→ 写路径塌陷相（80min，0 TPS）。触发条件是 TTL 600s
  过期（需求 33/s）≈ 回源通道容量（24-52/s）的零余量设计——缓存
  滑入未命中后永远追不平，拥塞沿共享路径（Router/连接池）传导到
  写事务，T+40min 起全部超过 1s 截止预算。EXP-16/17 的 12min 测试
  在结构上不可能看到：塌陷需要 40min 累积。这是「否定结论是有效
  结论」的直接例证。
- 拥塞塌陷为什么发生在写路径而不是读路径先死？
  → 读路径有三级保护（合并/12 槽位有界/200ms 等待），超限就 503
  明确拒绝，所以读「降级但不失控」；写路径的 6 语句事务 × qemu
  延迟本来就逼近 1s 预算，叠加 P1 行锁队列和回源占用连接池后越线
  ——写没有「拒绝保护」之外的降级模式（Outbox 语义要求写完整提交
  或明确失败），于是表现为全量 504。设计启示：写路径的预算余量
  必须显式核算「共享路径最坏拥塞时的延迟」。
- 组合故障为什么比两个单故障之和更糟？读路径哪里破了预算？
  → 单故障各自在有界机制内（EXP-08：stale 兜底；EXP-14：副本重建）；
  组合后 stale 库 1024 键 << 20000 键空间（工况迁移）+ Redis 无持久化
  恢复=冷缓存 → 重预热风暴。破预算的不是叠加，是工况变量（键空间）
  超出了单故障验证时的边界。
- Game Day 里「写路径为什么活着」？
  → 下单事务只依赖 MySQL（库存+订单+幂等+Outbox 同事务）；Redis 是
  可丢弃的读加速层，Pod 中断由剩余副本+K8s 重建承接——非核心依赖的
  故障被隔离在读路径内，核心写路径的可用性由架构保证。
- 「一次 Game Day 不能证明全年可用性 SLO」——那它证明了什么？
  → 证明了在声明的工况与容错预算内：症状告警全链路工作、写路径
  存活、数据零损伤、恢复路径收敛（含缓存重预热的真实成本）；同时
  暴露了读路径预算被工况迁移击穿的边界——这是 Game Day 的全部价值。
