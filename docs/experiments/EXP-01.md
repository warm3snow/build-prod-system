# EXP-01：业务契约、容量模型与实验边界

## 1. 实验目标

建立可验证的业务目标：明确 Flash Order 的业务语义、容量模型、SLO 与故障边界，
并用可编程断言固定数据不变量，作为后续所有实验的验收口径。

## 2. 背景问题

“高并发、高可用”在没有业务口径时无法验证：
- 不知道多少 QPS 算达标；
- 不知道什么错误算系统错误、什么算业务结果；
- 不知道哪些故障在保障范围内。

## 3. 初始架构

见 `docs/design/failure-domains.md`：Ingress → order-api × 1 → MySQL × 1。

## 4. SLA / SLO

| Metric | Target |
|---|---:|
| 查询 P99 | ≤ 200ms |
| 下单 P99 | ≤ 500ms |
| 系统错误率 | ≤ 0.1% |
| 可用性 | ≥ 99.95%（月度折算） |

完整口径见 `docs/design/sla.md`。

## 5. Baseline

本实验为设计基线，无实测数据（实测基线在 EXP-04 建立）。

| Metric | Before |
|---|---:|
| QPS | 无实现 |
| P99 | 无实现 |
| CPU | 无实现 |
| Memory | 无实现 |

## 6. Hypothesis

假设：先把业务完成标准、负载和故障范围写清楚，后续“高并发、高可用”才可验证。

## 7. 实验方案

1. 业务契约：单 SKU 单件、不补货不取消；下单成功＝库存与订单已提交。
2. 容量模型：缩尺档 1,000 QPS / 100 TPS，最终目标 5 倍线性放大。
3. SLO：正常态与故障态分离，错误分类固定。
4. 故障边界：明确单点清单，本地环境不宣称宿主机级 HA。
5. 可编程断言：库存守恒、幂等重放、同键冲突，用 Go 测试承载。

## 8. Code Change

- `internal/order/model.go`：领域类型与不变量（库存非负、幂等键、订单状态机初版）。
- `internal/order/model_test.go`：三个契约测试。
- `tests/load/smoke.js`：k6 冒烟脚本骨架，固定开放模型与 8:1:1 请求混合。

## 9. Kubernetes Change

本实验无部署变更；EXP-02 开始搭建最小运行底座。

## 10. Load Test

不适用（无服务可压）。EXP-04 执行。

## 11. Failure Injection

不适用（无运行系统）。故障矩阵见 `docs/design/failure-domains.md`。

## 12. Observability

不适用（EXP-04 引入）。本实验先定义错误分类与统计口径。

## 13. Results

| Metric | Before | After | Change |
|---|---:|---:|---:|
| 契约断言 | 无 | 3 个 Go 测试通过 | 新增 |
| 容量模型 | 无 | 缩尺档 1,000 QPS 目标 | 新增 |
| SLO 口径 | 无 | 已冻结 | 新增 |
| 故障边界 | 无 | SPOF 清单 | 新增 |

## 14. Root Cause

本实验无故障排查；它解决的问题是“验收口径漂移”——后续实验若没有固定口径，
容易用不同标准美化结果。

## 15. Trade-offs

- 缩尺档（1,000 QPS）便于本地复现，但最终目标需 5 倍放大验证，放大系数本身也是待验证假设。
- 单 SKU 单件简化了模型，代价是排除多商品订单的复杂度，后期如扩展需重审不变量。

## 16. Architecture Decision

- ADR-001：采用缩尺实验档，目标值写入 `docs/design/experiment-parameters.md`。
- ADR-002：错误分类以 `docs/design/sla.md` 为准，库存不足/限流不计入系统错误率。

## 17. Lessons Learned

- 先写口径再写代码，可以避免“压出结果再定标准”。
- 可用性分母要包含全部请求，否则 409/429 会把错误率“洗”成好看的数字。

## 18. Interview Questions

- 为什么 100 TPS 下单不代表系统只需要 100 QPS？
- P99 为什么比平均延迟重要？
- 幂等重放为什么不能重复扣库存？
- 本地单宿主机能证明什么、不能证明什么？
