# EXP-11：准入控制、时间预算与安全重试

## 1. 实验目标

- 主线落实令牌桶限流（429 明确拒绝）＋在途请求硬上限（503 明确拒绝），回答「过载如何被有界拒绝」；
- 从 EXP-02 的基本超时演进为**总截止时间约束**：入口、应用、DB、缓存、模拟依赖各层子预算由总预算推导，
  超时后通过 context 取消无用工作（DB 语句/回源随之终止）；
- 安全重试：只在明确可重试错误（死锁 1213/锁等待 1205）与幂等操作上启用退避＋抖动＋次数/总时长上限，
  测量客户端与存储层的**重试放大率**；
- 用固定到达率施加过载与临时失败，区分成功、业务拒绝、限流拒绝、过载拒绝与超时的分类计数。

## 2. 背景问题

EXP-04/09/10 已建立容量、事件链路与反压，但三个缺口仍存在：

1. **无准入边界**：超过容量的流量直接排队进入应用，延迟劣化、错误率飙升、客户端超时后重试，
   形成「过载→超时→重试→更过载」的自我放大（本实验场景 A1 实测 96% 失败）。
2. **无总时间预算**：DB（DSN 2s）、Redis（100ms）、回源（1s）各有独立超时，但没有端到端截止时间；
   一个请求可以在各层依次消耗时间，最坏 4s+ 才失败，占用连接与 goroutine。
3. **重试口径未冻结**：存储层死锁重试（EXP-03）没有退避抖动，客户端重试没有次数/总时长约束，
   下游抖动时各层重试会乘法放大（EXP-03 实测锁等待 22 万次已有先兆）。

## 3. 准入与预算链路（本实验冻结）

```text
入口（k6 客户端）：固定到达率；只对可重试错误重试（≤2 次、退避 50ms×2^n＋抖动、同幂等键）

order-api 中间件（由外向内）：
  [总时间预算] 读 500ms / 写 1s（context deadline，贯穿下游）
  [令牌桶限流] 1500 req/s + burst 300（单实例预算；N 副本总预算 = N × 单实例）
  [在途上限]   200（无队列，超过立即 503 overloaded）
  → 业务处理器（store.CreateOrder / 缓存读路径）

下游子预算（由总预算先行截断）：
  DB：DSN read/write 2s / 语句级；Redis：100ms/操作；回源：1s（读路径受总预算截断）
  存储层事务重试：最多 3 次、退避 25ms×2^(n-1)±50% 抖动、受请求 ctx 总预算约束
```

- **拒绝分类**（sla.md 口径）：429 `rate_limited` / 503 `overloaded` 是保护性拒绝，**不计系统错误率**、
  单独计数；504 `deadline_exceeded` 与 500 计入系统错误。
- **探针豁免**：`/healthz` `/readyz` 不消耗令牌与在途额度——过载时探针必须保持 2xx。
- **多副本口径**：令牌桶是单 Pod 预算，集群总预算按副本数线性放大；需要精确全局配额应在入口层再限
  （本课程入口为 k8s Service，只声明关系不实现分布式桶，EXP-13 按副本数核算）。

## 4. SLA / SLO（冻结）

| 指标 | 正常态 | 过载态（到达率 > 容量） | 临时失败态（DB 行锁 30s） |
| --- | ---: | ---: | ---: |
| 读 P99 | ≤ 200ms | 被拒绝或 ≤ 500ms 预算 | 回源受限允许 503 |
| 写 P99 | ≤ 500ms | 被拒绝或 ≤ 1s 预算 | ≤ 1s（504 明确分类） |
| 系统错误率（5xx 除 429/503） | ≤ 0.1% | ≤ 0.1%（拒绝不计） | 写路径允许失败，读路径受控 |
| 限流拒绝可见性 | 0 | 429 单独计数 | — |
| 重试放大率（reqs/iterations） | ≈ 1.0 | 有界（客户端 ≤ 3 请求/迭代） | 有界 |
| 探针 | 200 | **必须 200（豁免）** | 存活必须 200 |
| 库存守恒/幂等 | 成立 | 成立 | 成立 |

## 5. Baseline（来自 EXP-10 及本实验 B0）

- 单实例容量 ~2000 req/s（8:1:1 混合，EXP-04 冻结）；200 TPS 下单受 P1 单行锁限制。
- B0（本实验，200 rps 无故障）：0 失败、avg 2.93ms、p95 9.02ms——正常态对照。
- 存储层事务重试：固定 25ms 线性退避、无抖动（EXP-03 冻结值）。
- 健康探针与业务同路径、无豁免（EXP-02 实现）。

## 6. Hypothesis

1. 令牌桶 1500 rps + 在途 200 下，3000 rps 过载约 50% 被 429 干净拒绝，被接纳流量 P99 仍满足 SLO，
   系统错误率 ≤ 0.1%；对照 A1（无准入）失败率 >90% 且客户端重试放大；
2. 总时间预算让慢请求在 1s（写）/500ms（读）内得到 504 明确分类，并取消下游无用工作；
3. 临时失败下，无写预算（B1）时存储层 1205 重试 + 客户端重试形成乘法放大（DB 池饱和→读路径波击）；
   有写预算（B2）时故障被限制在写路径，放大有界；
4. 探针若与业务共用限流，过载时 liveness 会误判不健康重启 Pod（二次放大）——需要豁免。

## 7. 实验方案

1. **场景 A（过载对照）**：`tests/load/overload-retry.js`，constant-arrival-rate 3000 rps × 2min（8:1:1）：
   - A1：无准入无预算（RATE_LIMIT=0、MAX_INFLIGHT=0、READ/WRITE_BUDGET=0）；
   - A2：准入开（1500/300/200/500ms/1s）。
   记录：k6 到达率/丢弃、失败率、重试放大率（http_reqs/iterations）、延迟分位；
   服务端按 status 分类计数。
2. **场景 B（临时失败）**：200 rps × 90s，T+25s 起对 P1 inventory 行注入 30s 独占锁
   （`SELECT ... FOR UPDATE; SLEEP(30)`，holder 会话保活执行）：
   - B1：WRITE_BUDGET=0、innodb_lock_wait_timeout=1s、客户端超时 5s；
   - B2：WRITE_BUDGET=1s、innodb_lock_wait_timeout=2s、客户端超时 1.5s。
   记录：mysql_tx_retries_total、500/504 分类、在途 503、回源 503、readyz 失败、客户端放大率。
3. **对账**：压测前后 P1 库存扣减 == 新订单数；outbox/inbox/notif 1:1:1；幂等无孤儿记录。

## 11. Failure Injection

- 过载：到达率 3000 rps > 单实例容量 ~2000；
- 临时失败：MySQL 会话持 P1 inventory 行独占锁 30s（`FOR UPDATE` + `SLEEP(30)`，
  注意：`UPDATE t SET c=c` 需指定库名；holder 需 exec 会话保活，容器内 nohup 会被会话回收杀掉）；
- 附带发现：压测机自身资源不足（1 核/1Gi）会成为瓶颈（VU 封顶 826 → 丢迭代）——
  施压端资源必须与目标到达率匹配。

## 13. Results

实测环境：Rancher Desktop k3s（单机，16GB/6 核 VM），镜像 exp11b（A1 用 exp11a，无探针豁免影响）。

### 场景 A：过载对照（3000 rps × 2min）

| 客户端重试放大（reqs/iters） | 1.19× | 1.001× | A2 通过 |
| 延迟 p95 / max | 801ms / 1.62s | 91ms / 810ms | A2 通过 |
| 系统错误率（500+504） | 服务端数据因 VM 崩溃丢失 | **0.041%**（147/360257） | A2 ≤ 0.1% |
| 限流拒绝（429） | 0 | 180199（50.0%） | 拒绝分类可见 |
| 在途拒绝（503 overloaded） | 0 | 7054（2.0%） | — |

- **A1 的失败形态**：无准入时请求全部进入，服务端 CPU 打满、请求排队，客户端 400/800ms 超时后
  按原键重试 → 1.19× 放大 → VU 耗尽 → 迭代开始丢弃。首轮 A1 还曾把 k6 压测机（1Gi）OOM
  （exit 137）——**无界过载连施压端都会拖垮**。
- **A2 的拒绝形态**：50% 在入口被 429 干净拒绝（平均 18ms 内返回），接纳流量 P95 91ms
  （expected_response p95 148ms，满足读 200ms SLO）；写请求 100% 得到明确分类
  （201/200/409/429/503/504）。
- **探针 bug 证据**（exp11a 期间）：过载中 `/healthz` 被限流返回 429 → liveness 失败 →
  kubelet SIGTERM → Pod 在压测中途优雅退出（"order-api stopped"）重启。修复（探针豁免）后
  exp11b 全程 0 重启。**过载保护本身不能成为故障源**。

### 场景 B：临时失败（P1 行锁 30s，200 rps × 90s）

| 指标 | B0 无故障（对照） | B1 无写预算（锁等 1s） | B2 写预算 1s（锁等 2s） |
| --- | ---: | ---: | ---: |
| 客户端失败率 | 0% | 26.75% | 19.98% |
| 迭代时长 max / p95 | 94ms / 9ms | **15.21s** / 981ms | **3.23s** / 400ms |
| 写 500（重试耗尽，不可解释） | 0 | 56 | 0 |
| 写 504（明确分类） | 0 | 608（多为客户端断连） | **1042**（服务端预算，客户端可见） |
| `mysql_tx_retries_total` | 0 | **398** | 111 |
| 在途拒绝（503 overloaded） | 0 | 786 | 0 |
| 回源拒绝（503 backfill） | 0 | ~2900 | 2518 |
| readyz 失败次数 | 0 | 5（短暂摘流风险） | 0 |
| 客户端重试放大 | 1.0× | 1.036× | 1.040× |
| 库存守恒 | — | 成立 | 成立 |

**B1 的放大链条（自我放大的完整证据）**：行锁 → 写事务 1205 → 存储层退避重试（×3，398 次）→
每个写请求占连接 ~4s → DB 池（25）饱和 → 读路径（latest）等连接超 500ms → 504；
同时写请求占满在途额度（200）→ 新请求 503 overloaded（786）→ readyz 也拿不到连接（5 次失败）；
客户端 5s 超时后再重试，最坏迭代 15.2s。**一次 30s 的局部锁故障被重试放大成全链路抖动**。

**B2 的有界形态**：写请求 1s 预算到期 → 504 明确分类（客户端 1.5s 超时内可见）→ 连接 1s 即释放
（占用 20/25 池内）→ 无在途拒绝、无 readyz 失败、无 500；残余影响只剩缓存回源 503
（回源等连接的既有保护，EXP-08 语义）与 111 次死锁重试（锁释放瞬间的并发突发，有界退避吸收）。
**同一故障、同一负载，只差 1s 总预算：失败形态从「不可解释的 500 + 摘流 + 15s 长尾」变为
「写路径 504 + 读路径基本无损」**。

### 对账

- P1 库存扣减 66840 == EXP-11 全窗口新订单 66840（跨过载、VM 崩溃、锁注入全程精确守恒）；
- outbox SENT 837477 == inbox 837477 == notif 837477（1:1:1，无遗漏无重复副作用）；
- 幂等：无孤儿幂等记录（order_id=0 计数 0），客户端同键重试全部由 200 重放吸收。

### 事故记录（环境层面，非代码缺陷）

- A2 首轮压测（k6 2Gi + 3000 rps）中 Rancher Desktop VM 整体崩溃（k3s API server、dockerd 失联），
  `rdctl shutdown/start` 恢复后数据无损（PVC 完好、对账通过）。根因推断：单机 6 核 VM 上
  各组件 CPU limit 之和远超物理核数（mysql 2 + kafka 1 + api 2 + k6 2 + 监控栈若干），
  过载叠加时宿主资源耗尽。**3000 rps 是该环境的物理预算上限**，EXP-13 的资源预算表需以此为边界。

## 14. Root Cause

- **过载失败率 96% 的机制**：无准入时延迟与在途互相放大（Little's Law：在途 = 到达率 × 延迟），
  延迟劣化 → 客户端超时 → 重试增加到达率 → 更劣化。A2 的 429 在入口截断该循环。
- **探针重启的机制**：liveness 与业务共用限流器，429 被 kubelet 判为不健康；修复后探针豁免。
- **B1 放大链条**：无总预算时每个写请求的 DB 占用时间 = 锁等待 × 重试次数，40 conns 需求 > 25 池 →
  全链路等待。B2 的总预算把占用时间封顶 1s。
- **k6 施压端瓶颈**：1Gi/1 核下 VU 封顶 ~826（每 VU ~1.2MB），3000 rps × 阻塞时长超限即丢迭代；
  对照实验必须冻结施压端资源（本实验固定 2Gi/2 核）。

## 15. Trade-offs

- **限流拒绝优于排队**：429 让客户端立刻知道「过载」（可退避、可降级），排队只带来不可预测的
  超时与重试放大。代价：突发流量中一部分请求被拒（本实验 50%），保护的是已接纳流量与下游。
- **单实例限流不提供全局配额**：N 副本时总预算 = N×1500（EXP-13 核算），流量不均衡时单 Pod
  可能先打满；精确全局配额需要分布式限流或入口层再限（本课程不做）。
- **总预算 vs 独立超时**：总预算可能把「本来 1.5s 能完成」的请求在 1s 截断（假性超时）；
  对偶发慢查询不友好。缓解：预算取 SLO 的 2 倍以上余量，且只对可重试请求允许客户端重试。
- **客户端重试只限幂等写**：读请求不重试（本实验冻结），避免读放大；写重试依赖幂等键吸收，
  200 重放是预期行为而非错误。
- **探针豁免削弱了探针的「负载诊断」能力**：healthz 不再反映限流状态；限流健康由指标/告警观察
  （`ratelimit_requests_total` + `OrderAPIRateLimitedHigh`），探针只判存活。

## 16. Architecture Decision

- **ADR-022**：准入控制定为「总时间预算 → 令牌桶限流 → 在途上限」三层，拒绝分类
  429（限流）/503（在途）/504（预算）分别计数；限流为单实例预算，多副本总预算 = 副本数 × 单实例
  （EXP-13 起按此口径核算连接与限流预算）。
- **ADR-023**：健康探针豁免限流与在途上限——存活判定不依赖准入状态，准入状态由指标与告警承载。
- **ADR-024**：安全重试口径——存储层只在 1213/1205 上重试（指数退避＋抖动，≤3 次，受请求
  总预算约束）；客户端只对 status 0/5xx 的幂等写操作重试（≤2 次，退避＋抖动，同幂等键）；
  读路径与保护性拒绝（429/503/409）不重试。

## 17. Lessons Learned

- **过载保护本身会成为故障源**：限流器没有区分探针与业务流量，导致过载中 Pod 被自己的保护
  机制杀死（重启又放大过载）。任何准入机制都要先定义「谁豁免」。
- **压测机也是系统的一部分**：A1 的 96% 失败里混有压测机自身超时；k6 资源（1Gi/1 核）不足时
  数据直接失真（VU 封顶 826）。对照实验必须冻结施压端配置，且 `dropped_iterations` 必须为 0。
- **VM 级崩溃是「环境预算超支」的最强信号**：单机实验档的总 CPU limit 必须 < 物理核数
  （本环境各组件 limit 合计 > 6 核），EXP-13 的全局资源预算表要把它列为硬约束。
- **临时失败注入的工程细节**：`UPDATE t SET c=c` 会因未选库直接报错（看似注入了实际没有）；
  容器内 nohup 后台进程随 exec 会话回收被杀（锁根本没持有）。故障注入必须先验证
  「故障真实存在」（innodb_trx 可见 + 并发操作被阻塞计时）。
- **客户端断连被计入 504 是噪声**：B1 中 608 个「504」其实是客户端 5s 超时后断连的
  ctx.Canceled 映射。分类指标应区分「服务端预算耗尽」与「客户端放弃」，否则口径混乱。
- **单机环境的对照组必须串行**：A1/A2/B1/B2 共用同一 MySQL，前一轮的库存/连接池状态
  会污染后一轮；每次场景切换重启 order-api 并确认对账后再开始。

## 18. Interview Questions

- 为什么限流拒绝用 429 而不是 503？和「在途上限」的 503 有何区别？
  → 429 语义是「速率超预算，可稍后重试」，由令牌桶在入口给出，客户端应减速；
  503 overloaded 语义是「此刻并发已满，无法受理」，由在途计数给出。两者都是保护性拒绝、
  不计系统错误率，但 429 指向「请求太多」，503 指向「进程太忙」——排障方向不同。
- 总时间预算和独立超时（DB 2s、Redis 100ms）是什么关系？为什么不能只有后者？
  → 独立超时限制单层最坏时间，但各层可以串行叠加（DB 2s + 回源 1s + Redis 100ms×n）；
  总预算给出端到端上界并让「已经没希望」的请求提前放弃，释放连接/goroutine/在途额度。
  子预算由总预算截断：ctx 到期后所有下游操作自动取消。
- 为什么客户端重试只对「幂等写」启用？读为什么不能重试？
  → 写有幂等键，重试的同键请求由服务端 200 重放吸收，不产生重复订单；读重试放大高、
  收益低（读失败时下游大概率仍然失败），且读的幂等不解决「重试风暴」问题。
- 重试放大率怎么算？B1 的放大链条是什么？
  → 客户端放大 = http_reqs/iterations；存储层放大 = mysql_tx_retries_total。
  B1：锁 → 1205 → 事务重试 ×3（每个请求 4 次事务）→ 连接占用 ×4 → 池饱和 → 读等待超时 →
  在途额度耗尽 → 新请求 503 → 客户端超时再重试 → 更长的占用。每层放大相乘。
- 探针为什么要豁免限流？豁免后怎么知道系统在限流？
  → 探针的目标是「进程是否存活/就绪」，限流是准入策略不是健康状态；共用会导致过载时
  kubelet 误杀 Pod（本实验实测）。限流健康用 `ratelimit_requests_total` 与告警观察，
  与探针职责分离。
- 单实例 1500 rps 的限流在 3 副本时总预算是多少？有什么坑？
  → 4500 rps（线性放大）。坑：流量按连接均匀分布时成立，热点/粘性会话可能让单 Pod 先打满
  （429 早于集群容量耗尽）；且限流不与 DB/Redis 预算联动——总预算必须同时核算
  下游连接（EXP-13 口径）。
