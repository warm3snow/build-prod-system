# EXP-13：固定副本容量与 HPA 动态行为

## 1. 实验目标

- 关闭自动扩缩容，实测 1/2/4 副本的容量曲线：分别回答「扩容有效吗」（吞吐是否随副本增长）
  与「瓶颈在哪一层」（CPU / 限流 / DB 热点行 / 物理资源）；
- 计算全部 API、Relay、Consumer、发布余量的总连接预算，同步约束各副本的
  回源、限流与在途预算——**最大副本数不能突破下游预算**；
- 启用 HPA（CPU 利用率指标），测量指标采集、扩容触发、调度、就绪的完整时序；
  测试节点资源不足的 Pending 行为与缩容稳定性（不丢已提交业务）。

## 2. 背景问题

EXP-11/12 让单实例「过载有界、依赖故障可隔离」，但容量问题仍未回答：

1. **单实例容量已冻结**（EXP-04 ~2000 req/s、下单 200 TPS 受 P1 单行锁限制），
   但「加副本是否线性有效」从未实测——扩错方向比不扩更糟；
2. **预算未按副本核算**：限流 1500 rps、回源并发 12、DB 连接 25 都是单实例值；
   N 副本后总预算是否突破 MySQL max_connections、Redis、Kafka 的承受能力，没有表格；
3. **HPA 的指标与目标未校准**：requests=100m 是 EXP-02 的调度占位，
   利用率目标（70% × requests）因此失真；「扩得及时吗」「扩得对吗」没有证据。

## 3. 容量与预算模型（本实验冻结）

```text
副本容量模型：
  读路径：可水平扩展（缓存命中为主，CPU/限流是瓶颈）——实测线性
  写路径：P1 单行锁 ≈ 150-200 TPS 串行点——副本数不能改善，只会加长锁队列

连接预算（MySQL max_connections=151，EXP-06 连接池值）：
  API 25/副本 × N + Relay 4 + Consumer 16 = 25N + 20 ≤ 151 → N ≤ 5
  → HPA maxReplicas = 5（6 副本 170 连接会突破下游预算）

每副本预算（EXP-11/12 冻结值 × 副本数）：
  限流 1500 rps/副本（集群总限流 = N × 1500，无跨 Pod 协调）
  在途 200/副本；回源并发 12/副本（多副本回源合并仅限单进程，EXP-08 提示的放大点）
  依赖池 8/副本（熔断按副本独立计）

物理预算（单机 6 核 VM，EXP-11 事故边界）：
  各组件 CPU limit 合计 > 6 核时宿主资源耗尽（EXP-11 曾致 VM 崩溃）；
  requests 必须反映真实用量（本实验校准为 1 核/副本），否则调度与 HPA 同时失真
```

## 4. SLA / SLO（冻结）

| 指标 | 1 副本 | N 副本（N ≤ 5） | HPA 场景 |
| --- | ---: | ---: | ---: |
| 读 P99 | ≤ 200ms | ≤ 200ms | 扩容期间允许短暂抖动 |
| 写 P99 | ≤ 500ms | ≤ 500ms（受 P1 行锁约束，与副本数无关） | 同左 |
| 成功业务量 | 基线 | 读随副本线性，写不承诺增长 | 扩容不损害存量流量 |
| 扩容触发 → 就绪 | — | — | ≤ 2min（含指标采集与调度） |
| 缩容 | — | — | 0 已提交业务丢失、0 未完成消息跳过 |
| 最大副本 | — | ≤ 5（连接预算硬约束） | 同左 |
| Pending 行为 | — | — | 明确 Insufficient cpu，不抢占低优工作负载 |

## 5. Baseline（来自 EXP-04/11）

- 单实例混合负载（8:1:1）容量：EXP-04 冻结 ~2000 req/s（旧资源档）；
  本实验重新实测：**SLO 内混合容量 ≈ 1000-1200 rps**（见场景 E1，与 EXP-04 差异
  来自 EXP-09 后的 Outbox 固定开销与限流器）；
- 下单 P1 单行锁 ~150-200 TPS（EXP-04/09 已知热点）；
- requests=100m（EXP-02 占位值，本实验发现其导致 HPA 目标失真）。

## 6. Hypothesis

1. 读路径随副本线性扩展（每副本 ~1500 rps 限流预算内 CPU 有余量）；
2. 写路径受 P1 行锁限制，扩容无收益甚至恶化（更多并发事务加深锁队列）；
3. 限流预算随副本数放大后，把过载从入口转移到 DB 行锁——「扩容移除了保护」；
4. CPU 利用率 HPA 在「瓶颈不在 CPU」的场景会误扩（锁等待烧 CPU 被当成负载信号）；
5. requests=100m 的利用率目标失真（0.07 核/副本），必须按真实用量校准；
6. 缩容在端点摘除窗口内有短暂失败，但已提交业务不丢（优雅退出 + 幂等）。

## 7. 实验方案

1. **场景 E1（固定副本容量）**：删除 HPA，`tests/load/fixed-rate.js` 固定到达率：
   - 混合 8:1:1：1 副本 × {1000, 1500, 2000} rps、2 副本 × {2000, 3000} rps；
   - 纯读（READ_ONLY=1，隔离写瓶颈）：1 副本 × {1500, 2000}、2 副本 × {3000, 4000}；
   - 压测中观测 MySQL `Innodb_row_lock_current_waits` / `Threads_running`。
2. **场景 E2（HPA 动态行为）**：启用 HPA（CPU 70%，requests 100m——占位值先测再校准），
   2400 rps 混合 × 5min，记录 HPA 事件时序（指标可用 → SuccessfulRescale → Pod Ready）
   与业务吞吐；停载后记录缩容时序（稳定窗口 + 策略）。
3. **场景 E4（缩容稳定性）**：3 副本、800 rps 负载中缩容至 1，记录失败窗口、
   优雅退出与订单完整性。
4. **场景 E5（Pending）**：requests 校准为 1 核后 scale 至 8，观察
   `Insufficient cpu` 与无抢占行为。
5. **对账**：全程 outbox/inbox/notif 1:1:1；订单数 == 库存扣减；无孤儿幂等。

## 8. Code Change

- `tests/load/fixed-rate.js`（新增）：固定到达率 × 8:1:1 混合（READ_ONLY=1 纯读对照），
  read/write SLO 阈值编码为自动通过条件。

## 9. Kubernetes Change

- `deploy/k8s/base/all.yaml`：
  - 新增 HPA（autoscaling/v2，CPU 70%，min 1 / max 5——max 受连接预算约束，
    见第 3 节；scaleDown 稳定窗口 60s + 每 60s 最多缩 50%）；
  - 新增 PDB（minAvailable 1：自愿中断保护，不阻止硬故障与直接删除）；
  - order-api requests 校准：100m → **1 核**（真实用量，HPA 目标语义恢复）。

## 10. Load Test

- `fixed-rate.js`：constant-arrival-rate，RATE/DURATION/READ_ONLY 可配；
  dropped_iterations==0 自检；read P99 < 200ms / write P99 < 500ms 自动阈值。

## 11. Failure Injection

- 过载：混合负载到达率超过「写热点 + 限流」组合容量；
- 资源不足：requests=1 核下 8 副本 > 节点 6 核可分配 → Pending。

## 12. Observability

- HPA：`kubectl get hpa`（当前/期望副本、利用率）+ events（SuccessfulRescale 时间戳）；
- MySQL：`Innodb_row_lock_waits/current_waits`、`Threads_running/connected`（锁队列深度）；
- 沿用：RED、`orders_created_total`、限流/超时分类（EXP-11）、1:1:1 对账。

## 13. Results

实测环境：Rancher Desktop k3s（单机 6 核 / 16GB），order-api exp12b，MySQL 2 核。

### 场景 E1：固定副本容量曲线

**混合 8:1:1（写热点 P1）**

| 配置 | 到达率 | 读 P99 | 写 P99 | 失败率 | 判定 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1 副本 | 1000 | 142ms ✓ | 246ms ✓ | 0.68% | SLO 内 |
| 1 副本 | 1500 | 248ms ✗ | 494ms 边缘 | 1.53% | 读 SLO 破 |
| 1 副本 | 2000 | 292ms ✗ | 862ms ✗ | 28.0%（429 25%） | 限流+DB |
| 2 副本 | 2000 | **509ms** ✗ | **1.02s** ✗ | 23.6% | **劣于 1 副本** |
| 2 副本 | 3000 | 518ms ✗ | 1.06s ✗ | 70.9% | 明显劣化 |

**纯读（隔离写瓶颈）**

| 配置 | 到达率 | 读 P99 | 成功 | 备注 |
| --- | ---: | ---: | ---: | --- |
| 1 副本 | 1500 | 15.4ms | 100% | 限流预算内 CPU 有余量 |
| 1 副本 | 2000 | 18.8ms | 75.1% | 25% 429（限流 1500 封顶） |
| 2 副本 | 3000 | 50.5ms | 98.5% | **线性扩展** |
| 2 副本 | 4000 | 78.0ms | 75.2% | 25% 429（限流 3000 封顶） |

**写路径证据（2 副本 2000 rps 压测中）**：`Innodb_row_lock_current_waits` = **40**
（40 个事务同时在 P1 行上排队）；25s 内 `Innodb_row_lock_waits` +3311（~132 次/s）；
`Threads_running` 41、`Threads_connected` 60——**瓶颈是数据库热点行，不是 CPU**。

**结论**：
- **读路径扩容线性有效**（1→2 副本，限流预算内吞吐翻倍、P99 仅 15→50ms）；
- **写路径扩容无效甚至有害**：P1 行锁是 ~150-200 TPS 的串行点。1 副本时限流器
  （1500）在入口挡掉超额流量，DB 只承受 ~100-150 写/s；2 副本限流预算翻倍后
  全部放行，200+ 写/s 直达行锁 → 队列 40 深 → 写 P99 从 494ms 恶化到 1.02s，
  读路径也被 DB 连接池排队拖垮（P99 509ms）。**扩容移除了限流保护，
  把过载从入口转移到了数据库**。

### 场景 E2：HPA 动态行为（2400 rps 混合 × 5min，CPU 70% 目标）

| 阶段 | 时间 | 事件 |
| --- | ---: | --- |
| T+0 | 0s | 负载开始（HPA requests 尚为占位值 100m） |
| T+15s | 15s | metrics-server 首次返回指标（FailedGetResourceMetric 消失） |
| T+15s | ~15s | SuccessfulRescale：利用率 617% → desired=9 → 封顶 **max=5**，一步 1→5 |
| T+30-90s | | 5 副本全部 Ready（调度 + 启动 + 就绪 ≈ 30-75s） |
| T+5min | | 负载停止 |
| T+5min+75s | | 缩容 5→2（60s 稳定窗口 + HPA 同步 + 每 60s 最多 50%） |

**扩容及时但不正确**：
- 及时性 ✓：指标可用后 15s 触发、60-90s 内 5 副本就绪——「扩得及时」成立；
- 正确性 ✗：5 副本下业务反而更差（44.9% 失败、读 P99 690ms、写 P99 1.33s，
  对比 1 副本 1000 rps 的 0.68% 失败）。**CPU 利用率高企的原因是事务在 DB 行锁上
  等待烧 CPU，HPA 把「锁等待」误判为「计算不足」，扩容方向错误**。
- 目标失真：requests=100m 时「70% 利用率」= 0.07 核/副本，语义上不是任何真实容量
  信号；校准为 1 核后目标恢复含义（~1 核/副本 × 70%）。

### 场景 E4：缩容稳定性（3 副本、800 rps 负载中 → 1 副本）

- 检查通过率 97.17%、失败 2.82%——失败集中在端点摘除窗口（terminating Pod 仍短暂
  在端点列表中，新请求被拒/连接重置，~2.5s 流量）；
- 优雅退出生效：在途请求由 15s grace 期完成，无 500 堆叠；
- 订单完整性：窗口内 28496 个新订单全部 SENT、1:1:1 对账成立——**0 已提交业务丢失**。

### 场景 E5：节点资源不足的 Pending（requests=1 核，scale → 8）

- 8 副本请求 8 核 > 节点可分配（6 核 - 其他工作负载 ~4 核）→ 5 副本调度成功后
  其余 **Pending**：事件 `0/1 nodes are available: 1 Insufficient cpu`、
  `No preemption victims found`——无抢占（本课程工作负载无 PriorityClass 差异，
  符合预期）；缩回 1 副本后立即恢复。

### 对账

- outbox SENT 943981 == inbox 943981 == notif 943981（全程 1:1:1，含扩容/缩容/Pending 混沌）；
- 幂等无孤儿；P1 库存守恒（订单增量 == 库存扣减）。

## 14. Root Cause

- **读扩容线性的机制**：读路径 ~90% 缓存命中，CPU 消耗极低（1500 rps 时 P99 15ms、
  单副本 CPU 余量充足），副本数直接放大限流预算与吞吐。
- **写扩容负收益的机制**：P1 行锁把写串行化在 ~150-200 TPS；副本增加的是
  「锁队列中的等待事务」而不是「完成的事务」——更多连接被占用（60 连接）、
  更多死锁重试、读路径的连接池被挤占。限流预算随副本放大后，
  过载从「入口 429」变成「DB 锁队列」。
- **HPA 误扩的机制**：CPU 利用率 = 实际用量 / requests；请求在 DB 上等待时
  goroutine/驱动轮询烧 CPU，因此「DB 瓶颈」在指标上表现为「CPU 高」。
  CPU HPA 只保护计算资源，无法感知下游瓶颈（roadmap 明确预期此风险）。
- **缩容失败窗口**：endpoint slice 更新与 Pod 终止存在秒级竞态，请求落入
  已终止 Pod → 连接拒绝；k8s 的标准行为，P99 影响在几百毫秒级。

## 15. Trade-offs

- **CPU HPA vs 业务指标 HPA**：CPU 指标免费、无需改造，但在「瓶颈不在 CPU」时误扩
  （本实验实证）。业务指标（如成功 TPS、写队列深度）更准确但需要自定义指标链路
  （Prometheus Adapter），本课程主线只落实 CPU 并如实报告其边界；
  KEDA/自定义指标为选做。
- **maxReplicas=5 是「保护下游」而非「容量目标」**：连接预算 25N+20 ≤ 151 的
  推导下 5 是硬上限；即便节点能调度更多副本，超过 5 会开始挤占 Relay/Consumer
  的连接（三者共享 MySQL）。
- **requests 提至 1 核的代价**：调度更保守（真实占用），单机可排副本数变少
  （本环境 8 副本即 Pending）；换来的 HPA 目标语义正确。requests 是「调度承诺」，
  limit 是「隔离上限」，两者分离（1 核 request / 2 核 limit）保留突发余量。
- **缩容 50%/60s 策略**：保守（避免抖动），代价是缩容慢（5→1 需 ~3 分钟）；
  对成本敏感场景可调激进，但快速缩容 + 流量回弹会形成扩容震荡。

## 16. Architecture Decision

- **ADR-027**：横向扩容策略定为「读路径水平扩展 + 写路径瓶颈显式化」：
  HPA 仅以 CPU 指标驱动（max 5，受连接预算约束），写路径的 P1 热点在
  本课程范围内**不通过扩容解决**（分桶/拆 SKU/队列化下单属于业务改造，超出
  课程主线）；限流预算按副本数线性核算（EXP-11 口径落地）。
- **ADR-028**：资源 requests 从「调度占位」改为「真实用量」：requests=1 核
  （1000 rps 混合负载实测），HPA 利用率目标恢复语义；所有后续实验的预算表
  以该值冻结。

## 17. Lessons Learned

- **扩容前先问瓶颈在哪**：本实验的写路径是教科书级反例——加副本后吞吐不升反降。
  「扩容有效吗」必须先于「扩得及时吗」回答；CPU HPA 在 DB 瓶颈下会持续扩到 max
  并恶化业务。
- **限流预算是「入口保护」不是「容量目标」**：副本数放大限流预算的同时，
  必须确认下游（DB 行锁/连接/磁盘）能承受放行后的流量，否则扩容等于
  亲手拆掉自己的保护（2 副本 2000 rps 的 40 深锁队列）。
- **requests 占位值会静默腐蚀 HPA**：100m 的 requests 让「70% 利用率」变成
  0.07 核的伪目标；一切利用率型自动化的前提是 requests 反映真实用量。
- **apply 会覆盖 patch**：`kubectl apply -f` 全量清单会重置手工 patch 的
  requests（本实验 HPA 测试一度跑在未校准值上）；实验中途改资源要回到
  单一事实源（all.yaml）修改。
- **Pending 是预算超支的安全形态**：`Insufficient cpu` + 无抢占是单机环境
  最干净的超支表现（等待而非乱杀）；如果启用了抢占，低优工作负载会被驱逐，
  优先级设计必须先于「允许抢占」的决策。
- **缩容的失败窗口可预期**：端点摘除竞态带来的 ~2.5s 失败窗口是 k8s 标准行为，
  客户端重试（EXP-11 口径）+ 优雅退出足以吸收；不要试图「零失败缩容」。

## 18. Interview Questions

- 为什么 2 副本 2000 rps 比 1 副本 2000 rps 更差？
  → 1 副本时限流 1500 在入口拒绝 25%，DB 只承受 ~100 写/s；2 副本限流预算 3000
  全放行，200+ 写/s 直达 P1 行锁（~150-200 TPS 串行点），队列加深到 40，
  写延迟恶化、连接被占、读路径排队。扩容放大了限流预算，把过载从入口搬到 DB。
- 扩容对什么负载有效？对什么无效？
  → 对缓存命中的读路径线性有效（纯读 2 副本 3000 rps P99 50ms）；
  对写热点（P1 行锁）无效且有害。判定依据不是「CPU 高不高」而是
  「瓶颈在哪一层」（行锁队列深度 40 是直接证据）。
- CPU HPA 为什么会误扩？什么指标更合适？
  → 请求在 DB 上等待时烧 CPU（轮询/上下文切换），CPU 利用率反映的是「忙碌」
  而不是「有效工作」；DB 瓶颈下加副本只会加锁等待。更合适的指标是业务指标
  （成功下单 TPS、写队列深度、行锁等待）或 DB 侧信号，需要自定义指标链路。
- maxReplicas=5 是怎么算出来的？
  → MySQL max_connections=151；API 25/副本 + Relay 4 + Consumer 16：
  25N+20 ≤ 151 → N ≤ 5。超出的副本无法获得数据库连接，扩容失去意义。
  这是「扩容预算受下游约束」的量化表达。
- 为什么 requests 要从 100m 改成 1 核？这改变了什么？
  → requests 是调度承诺与 HPA 利用率的分母。100m 时「70% 目标」= 0.07 核，
  任何真实负载都会触发满额扩容；1 核（实测 1000 rps 混合负载的真实用量）后
  目标语义恢复为「每副本 CPU 用满 70% 时扩容」。代价是调度更保守（可排副本变少）。
- 缩容时的 2.82% 失败能消除吗？为什么不必消除？
  → 不能完全消除：endpoint slice 传播与 Pod 终止存在秒级竞态。正确做法是
  客户端对可重试错误按原键重试（EXP-11）+ 优雅退出（15s grace 完成在途请求），
  已提交业务 0 丢失（本实验 28496 单全部 SENT）。追求「零失败缩容」会引入
  复杂的连接排空/延迟摘流机制，收益不成比例。
