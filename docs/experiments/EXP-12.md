# EXP-12：熔断、资源隔离与业务降级

## 1. 实验目标

- 用可控依赖模拟器（商品附加信息）复现「慢响应」与「持续失败」两类非关键依赖故障；
- 对照验证：无隔离时慢依赖如何耗尽共享资源（在途额度/连接/goroutine），
  逐项加入**并发隔离**（有界池 + 有界等待 + 独立超时）与**熔断**后的收益；
- 验证熔断三态（closed/open/half-open）完整生命周期与恢复轨迹：探测并发受限、
  恢复不形成请求洪峰；
- 定义可接受的降级结果：商品附加信息可省略（200 + `X-Dep: degraded`），
  库存事务与幂等约束不经过依赖、不可绕过。

## 2. 背景问题

EXP-11 的准入控制让「过载」有界，但一个缺口仍在：**依赖故障**。

1. 慢依赖（如 2s 延迟的推荐服务）会长时间占用请求处理资源：进程 goroutine、
   HTTP 连接、EXP-11 的在途额度（200）——这些资源与核心下单/查询**共享**。
   没有隔离时，非关键依赖可以饿死核心路径（本实验 C1 实测核心读通过率仅 16%）。
2. 持续失败的依赖没有「快速失败」通道：每个请求都实打实地等超时/拿错误，
   失败成本恒定叠加；也没有机制避免对已知故障的依赖继续发请求（打坏下游、拖慢自己）。
3. 降级语义未定义：依赖故障时应该返回什么、如何标记、什么不能降级——都没有契约。

## 3. 依赖链路（本实验冻结）

```text
GET /api/products/:sku/extra（独立于下单路径）
  └─ resilience.Client（product-extra）：
       [隔离] 并发信号量 8 + 连接上限 8 + 有界等待 50ms（拿不到槽位 → 降级，不排队）
       [熔断] 连续失败 5 次 → open（10s 冷却）→ half-open（探测并发 1）→ 成功关闭
       [超时] 单次调用 200ms（写路径 1s 总预算的子预算，EXP-11 口径）
  └─ dependency-simulator（/extra/:sku；/control 实时注入 slow/fail）
      降级契约：依赖不可用 → 200 + {"extra": null, "degraded": true} + X-Dep: degraded

核心路径不变：下单事务（库存+订单+幂等+Outbox）与商品/库存查询
  不经过模拟器；任何依赖降级都不能绕过核心数据校验。
```

- **降级是「省略非关键字段」不是「伪造成功」**：响应 200 但 `degraded: true` +
  `X-Dep: degraded` 头 + `dep_degraded_total` 指标，客户端可区分完整成功与降级成功。
- **熔断按连续失败计数**（5 次）而非失败率：依赖由好转坏时反应最快；半开探测并发 1，
  恢复时不会对刚恢复的下游形成洪峰。

## 4. SLA / SLO（冻结）

| 指标 | 依赖正常 | 依赖慢（2s） | 依赖持续失败 |
| --- | ---: | ---: | ---: |
| 核心读 P99 | ≤ 200ms | **≤ 200ms（不被波击）** | 同左 |
| 核心写 P99 | ≤ 500ms | **≤ 500ms（不被波击）** | 同左 |
| 核心下单成功 | 正常 | **必须保持** | **必须保持** |
| extra 响应 | 200 + extra | ≤ 50ms 内降级（200+degraded） | 熔断后即时降级 |
| 依赖调用预算 | — | 并发 ≤ 8 | 熔断打开期间 ≈ 0（仅探测） |
| 降级可见性 | 0 | X-Dep: degraded 可观测 | 同左 + 熔断状态指标 |
| 恢复 | — | 依赖恢复后自动恢复 | ≤ 冷却期 + 探测延迟 |

## 5. Baseline（来自 EXP-11 与 C0）

- C0（依赖正常，1000 rps，1min）：0 失败；core-read p95 13.2ms、core-write p95 48.2ms；
- 在途上限 200（EXP-11 冻结）：慢依赖无隔离时会占用该共享额度；
- 读路径总预算 500ms：无隔离时被慢依赖占住的请求在 500ms 被 504（客户端已超时）。

## 6. Hypothesis

1. 无隔离时慢依赖（2s）把共享在途额度（200）占满，核心读写被 503 波击（通过率骤降）；
2. 隔离（池 8 + 等待 50ms + 超时 200ms）把依赖并发锁死在 8，核心路径与基线一致；
3. 熔断在持续失败下快速打开，打开期间模拟器收到的调用趋近于零（只有半开探测）；
4. 依赖恢复后，半开探测成功 → 自动关闭，恢复延迟 ≈ 冷却剩余时间（≤ 10s）；
5. 降级响应（200+degraded）可观测、可区分，不伪装成完整成功。

## 7. 实验方案

1. **场景 C0（正常态基线）**：sim mode=ok，1000 rps × 1min（`tests/load/extra-info.js`，
   混合：extra 60% / 商品读 30% / 库存读 5% / 下单 5%）。记录核心延迟与依赖延迟。
2. **场景 C1（无隔离对照）**：`DEP_ISOLATION=false`、`DEP_POOL_SIZE=0`、`DEP_TIMEOUT=2s`，
   sim slow 2s，1000 rps × 1min。记录核心通过率、503 分类、模拟器收到的调用数与总延迟。
3. **场景 C2（隔离+熔断）**：`DEP_ISOLATION=true`、池 8、超时 200ms，sim slow 2s，
   1000 rps × 1min。记录同 C1 指标，对照。
4. **场景 C3（熔断生命周期与恢复）**：隔离配置同 C2，sim fail（fail_rate=1.0）
   1000 rps × 2min，T+60s 恢复 sim 为 ok。记录熔断状态迁移、短路计数、恢复后 ok 计数与恢复延迟。
5. **对账**：outbox/inbox/notif 1:1:1；幂等无孤儿；核心下单数 == 库存扣减数。

## 13. Results

实测环境：Rancher Desktop k3s（单机），order-api 镜像 exp12a，模拟器 exp12a。
混合负载 1000 rps（extra 60% / 商品读 30% / 库存读 5% / 下单 5%）。

### 场景 C0：正常态基线（1min）

100% 检查通过、0 失败；core-read p95 13.2ms、core-write p95 48.2ms、
extra 平均 5.6ms——后续场景的对照锚点。

### 场景 C1：无隔离 + 慢依赖 2s（1min，DEP_ISOLATION=false）

| 指标 | 实测 |
| --- | ---: |
| 核心商品读通过率 | **16%**（2866/17803） |
| 核心库存读通过率 | **16%** |
| 在途拒绝（503 overloaded） | **50170** |
| extra 被准入请求 | 6000（占满在途额度，每个占满 2s） |
| extra 被 503 拒绝 | 30172 |
| 模拟器收到调用 / 总延迟 | 6000 次 × 2s = 12017s |
| 核心读 P99 | 无法满足 SLO（84% 被拒绝） |

- **慢依赖耗尽共享资源**：6000 个 extra 请求 × 2s 持续占用全部 200 个在途槽位整整 60s
  （6000×2s/60s = 200 槽位全满），核心读写 84% 被 503 拒绝；这 6000 个请求的响应
  在客户端超时（500ms 预算）后才写完，属于白做的无用工作。
- 有意思的是 EXP-11 的准入控制起了「缓冲」作用：如果没有在途上限，这里将是
  1200 个并发 goroutine/连接（600 rps × 2s）而非 200——但 200 的全额占用
  已足以饿死核心路径。

### 场景 C2：隔离 + 熔断 + 慢依赖 2s（1min）

| 指标 | 实测 |
| --- | ---: |
| 整体检查通过率 | 99.62% |
| 核心商品读通过率 | **99.6%** |
| 在途拒绝 | **0** |
| 超总预算（504） | **0** |
| extra 响应 | 36096 全部 200 + degraded（约 50ms 内降级） |
| **模拟器收到调用** | **14 次**（对比 C1 的 6000 次） |
| 熔断迁移 | open ×6、half-open ×5（10s 冷却循环） |
| 核心延迟 | 与 C0 基线一致 |

- **隔离把依赖并发锁死在 8**，慢依赖最多占用 8 个槽位，核心路径分走其余 192；
- **熔断让「已知故障的依赖」几乎零负载**：60s 内模拟器只收到 14 次调用
  （初始 closed 阶段的 8 并发 + 半开探测），其余 36040 次全部短路（circuit_open）；
- 降级请求平均 ~2ms 返回（avg 整体 2.23ms），核心读写与基线无差别。

### 场景 C3：持续失败 60s → 恢复 60s（2min）

| 阶段 | 观测 |
| --- | --- |
| 0-60s（fail 100%） | 前几个调用失败（error 6 + timeout 14）→ 连续失败 5 次 → 熔断打开；60s 内 12 次 open/half-open 循环（10s 冷却 + 探测失败）；`circuit_open` 短路 71969 次，全部即时降级 |
| 60-120s（恢复 ok） | 半开探测成功 → 熔断关闭（`to=closed` ×1）；随后 35865 次调用全部 ok（模拟器计数 35871 精确一致） |
| 最终状态 | `dep_circuit_state = 0`（closed），0 失败 |

- **恢复轨迹完整**：打开 → 冷却 → 半开探测（并发 1，不形成洪峰）→ 关闭，
  恢复延迟受冷却期约束（≤ 10s + 探测耗时）；
- 降级计数 72045 vs 正常 35865：`dep_degraded_total` 与模拟器调用数可以相互对账，
  降级响应（200+degraded）与完整成功可区分——**降级没有伪装成完整成功**。

### 对账

- outbox SENT 860334 == inbox 860334 == notif 860334（1:1:1，全程含依赖故障期）；
- 幂等无孤儿（order_id=0 计数 0）；EXP-11/12 全窗口库存守恒保持成立。

## 14. Root Cause

- **C1 的饿死机制**：慢依赖的每个请求占住在途槽位 2s，而正常请求只需 2ms——
  同一槽位吞吐相差 1000 倍；60% 的依赖流量足以让槽位永远被慢请求占满。
- **熔断收益的来源**：与其说熔断「保护下游」，不如说它把「已知的失败」从
  「每请求实打实等超时」（C1：2s 占用）变成「即时短路」（C2/C3：~1ms 降级）。
  失败成本的差异直接决定了共享资源是否被耗尽。
- **半开探测并发 1 的必要性**：恢复瞬间如果放行全部积压流量，会像 C1 一样
  把刚恢复的依赖打慢（甚至再次触发熔断）；单探测 + 成功后关闭保证恢复渐进。

## 15. Trade-offs

- **熔断的误伤窗口**：冷却期内即使依赖已恢复也要等到半开探测才放行（本实验 ≤10s），
  期间全部降级。对「附加信息」类依赖可接受；对核心依赖不可接受——核心依赖不能熔断，
  只能走超时/重试/预算（EXP-11 口径）。
- **降级是产品契约不是技术兜底**：`degraded: true` 需要客户端配合渲染降级 UI；
  若客户端把 null extra 当错误，降级反而制造告警风暴。契约必须在接口文档声明。
- **连续失败阈值 vs 失败率**：阈值 5 对「偶发失败」敏感（慢依赖 C2 中因超时连败快速打开——
  这恰好是期望行为）；对「部分失败」场景（如 30% 失败率）可能抖动。失败率模型
  需要窗口统计，本课程单依赖场景不采用（roadmap：多种熔断算法为选做）。
- **隔离池按依赖分账**：池 8 是「product-extra」独占预算；未来新增依赖必须单独预算，
  不能共享一个池（共享池会让慢依赖互相挤压——正是本实验要避免的问题）。

## 16. Architecture Decision

- **ADR-025**：非关键依赖统一走「隔离（有界池 + 有界等待 + 独立超时）→ 熔断 →
  降级（200+degraded）」链路；依赖预算独立于核心路径，降级语义由响应头/响应体/指标
  三层可观测。核心数据校验（库存/幂等）不允许熔断或降级。
- **ADR-026**：熔断采用连续失败计数模型（阈值 5、冷却 10s、半开探测并发 1），
  按依赖实例化（label=dep 名），后续依赖复用同一实现、独立配置。

## 17. Lessons Learned

- **慢比失败更危险**：fail 模式（C3）在熔断下 60s 内就被短路；slow 模式（C2）在无隔离
  时是最隐蔽的资源杀手（每个请求看起来「还在处理」，实际全在等待）。依赖保护必须
  同时覆盖慢与失败，超时预算比熔断更基础。
- **共享额度被谁占用是可观测的**：C1 的 50170 次 503 里核心与依赖各占多少，靠
  `http_requests_total{route}` 与模拟器 `/state` 调用数对账才能讲清楚——
  故障分析不能只看总量。
- **模拟器是故障注入的「独立账本」**：应用侧指标（dep_requests_total）与模拟器侧计数
  （calls）互相印证（C3：ok 35865 vs calls 35871），能发现「调用发了但没到下游」
  这类隐蔽问题。
- **对照实验要重置计数器**：C1/C2 共用模拟器与 order-api，若不重启模拟器，
  累计调用数会混叠（首次 C2 复测时 113581 次调用无法归因）；每个场景前
  `rollout restart` 依赖与目标组件。
- **k6 handleSummary 覆盖默认输出**：自定义 summary 会吞掉 TOTAL RESULTS；
  实验数据输出要保留默认汇总（本实验把降级计数放到服务端指标，客户端只留响应头核对）。

## 18. Interview Questions

- 为什么非关键依赖可以「熔断 + 降级」，核心依赖（MySQL）不能？
  → 附加信息的缺失有明确的产品语义（省略字段），且其失败不破坏任何业务不变量；
  核心依赖承载库存事务与幂等约束，「熔断」等于把数据校验停掉，任何假成功都不可接受。
  核心依赖的故障处理是超时/预算/重试（EXP-11），不是熔断。
- 隔离池 8 是怎么定的？为什么有界等待 50ms 而不是无限排队？
  → 池大小 = 依赖能承受的并发 × 单副本预算（8 个 200ms 调用 = 最多 40 req/s 实际吞吐，
  不足部分全部降级）；无限排队等于把进程变成依赖的缓冲池——goroutine 无限堆积，
  与无隔离等价。有界等待保证「降级延迟有上界」（~50ms）。
- 半开探测为什么并发限制为 1？如果恢复瞬间放行 1000 个请求会怎样？
  → 1000 个请求会同时打向刚恢复的依赖（可能就是它刚被打挂的原因），大概率再次失败
  → 熔断重新打开 → 抖动循环。单探测成功后逐步放行，恢复渐进、可观测。
- 熔断打开期间的请求哪里去了？降级响应为什么是 200 而不是 503？
  → 请求在 order-api 内短路（circuit_open 计数），返回 200+degraded。用 200 是因为
  「商品查询」这个业务操作仍然成功（只是少一个非关键字段）；用 503 会把非关键依赖
  的故障伪装成核心接口的故障，错误分类失真。降级可见性由 X-Dep 与指标保证。
- C1 里 6000 个 extra 请求的响应为什么「白写了」？
  → 服务端 2s 后才完成，但读路径总预算 500ms（EXP-11）与客户端超时（500ms）都更早；
  响应写出时客户端已断连。这些请求占用的槽位/连接/goroutine 全部是无用功——
  「超时后取消无用工作」的前提是调用链路遵守 context（本实验模拟器调用未用请求
  ctx，属遗留缺陷，见 Trade-offs 与后续修复计划）。
- 依赖恢复后多久恢复正常？这个延迟由什么决定？
  → ≤ 冷却剩余时间 + 一次探测耗时（本实验 ≤ ~10s）。冷却期越短恢复越快但抖动风险越高；
  冷却期是「给依赖喘息时间」与「尽快恢复服务」的折中。
