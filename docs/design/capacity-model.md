# 容量模型

## 1. 业务假设

| 指标 | 缩尺实验档（本地） | 最终目标 | 放大系数 |
|---|---:|---:|---:|
| DAU | 200,000 | 1,000,000 | 5x |
| 峰值在线用户 | 10,000（DAU 的 5%） | 50,000 | 5x |
| 峰值请求 QPS | 1,000 | 5,000 | 5x |
| 峰值下单 TPS | 100 | 500 | 5x |
| 峰值订单查询 QPS | 100 | 500 | 5x |

- **请求混合**：商品/展示库存查询 80%，创建订单 10%，订单结果查询 10%。
- **数据规模（缩尺档）**：商品 10,000，注册用户 50,000，订单随压测时间增长。
- **模型假设**：每次下单只购买 1 个 SKU 的 1 件；主线不补货、不取消、不退款。
- **热点假设**：约 10% 商品承担 80% 查询流量（Zipf 近似），需在压测数据生成时实现。

## 2. 推导链

```text
DAU → 峰值在线（在线率 5%）
    → 峰值请求（人均请求强度 × 并发 × 峰值系数）
    → QPS 与 TPS 分离
```

- QPS 是每秒请求数（含读），TPS 是每秒完成的业务事务数（下单）。
- **100 TPS 下单 ≠ 系统只需要 100 QPS**：
  - 每笔订单还附带商品查询、订单查询等读流量；
  - 每笔订单在 DB 侧通常不止一次写（库存扣减、订单落库、幂等记录）；
  - 峰值系数与请求混合决定总 QPS 必须按 1,000 设计。

## 3. 峰值估算

以 8:1:1 请求混合计算缩尺档：

| 项 | 计算 | 结果 |
|---|---:|---:|
| 峰值总请求 | 给定 | 1,000 QPS |
| 商品查询 | 1,000 × 80% | 800 QPS |
| 创建订单 | 1,000 × 10% | 100 TPS |
| 订单查询 | 1,000 × 10% | 100 QPS |
| DB 写放大 | 每单≈2 次写（库存＋订单/幂等） | 150～200 写 QPS |
| DB 总读写 | 读查询＋写放大＋订单查询 | ≈ 1,100～1,150 QPS（粗估，EXP-04 实测修正） |

## 4. 资源水位与扩容线

- **安全水位**：CPU ≤ 60%（均值）、内存 ≤ 70%、DB 连接 ≤ 60% 上限、Kafka 磁盘 ≤ 60% 保留水位。
- **扩容触发**：CPU 持续超过安全水位、DB 连接等待上升、P99 突破 SLO 或错误率劣化，先验证瓶颈再扩容。
- **容量上限（实测前不宣称）**：缩尺档先按 1,000 QPS 目标验证，极限值由 EXP-04 压测决定。

## 5. 各阶段依赖的容量假设

| 阶段 | 关键容量假设 | 验证实验 |
|---|---|---|
| Phase 0 | 无缓存、无 MQ，DB 为瓶颈 | EXP-04 |
