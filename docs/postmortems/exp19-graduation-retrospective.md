# EXP-19 毕业复盘：Production System Lab 全程回顾

> 19 个必做实验（EXP-01～19）完成后的架构取舍与故障复盘。
> 对应 roadmap §5 EXP-19 第 5 条：哪些组件值得保留、容量边界在哪里、
> 哪些结论只在本地模拟成立。

## 1. 最终架构（一句话版）

模块化单体（Go）＋ InnoDB Cluster 单主 ×3 + Router ×2 ＋ KRaft combined ×3 ＋
Redis 单实例（纯缓存）＋ K8s 声明式部署 ＋ Prometheus/Grafana/k6——
**事件真相在 MySQL（Outbox/Inbox 同事务），Kafka 与 Redis 都是可重建、
可丢弃的加速层**。这是全程最重要的一条架构决定（EXP-09 定型，
EXP-17/18 两次兑现价值：换 Kafka 集群是运维操作，Redis 挂了写路径不受影响）。

## 2. 值得保留的组件与机制（按兑现次数排序）

| 机制 | 出处 | 兑现场景 |
| --- | --- | --- |
| Outbox/Inbox 同事务 + event_id 三段贯穿 | EXP-09 | 17/18 的每次故障对账；Kafka 集群替换；DR 重放去重 |
| 幂等键绑定用户+操作+参数（DB 约束） | EXP-03 | 一切重试/重放/DR 场景的收敛锚点 |
| 有界准入（令牌桶+在途上限+总截止时间） | EXP-11 | 900 rps 过载复核（D2）：明确拒绝而非雪崩 |
| 有界回源（合并+并发上限+stale 降级） | EXP-08 | Game Day 读路径「劣化但不打穿 DB」 |
| 库存差分守恒对账 + 客户端账本 | EXP-03/18 | 每次实验的终局裁判；RPO 的判定性证据 |
| GORM→真 INSERT IGNORE（GR 兼容） | EXP-16 | HA 档全部写路径 |
| 受控恢复顺序 Runbook | EXP-18 | DR 恢复零污染 |

## 3. 容量边界（实测数字）

- **稳态容量**：日常档（单实例 MySQL 直连）1000-1200 rps；
  HA 模拟档 600 rps——**缩尺全部来自 qemu 模拟的 Router（~8×CPU）**，
  MySQL 集群本身不是瓶颈（EXP-16）；
- **写路径真瓶颈**：P1 单行锁 + 每事务 6 语句 × Router 延迟（EXP-06/13），
  加副本不能提升写吞吐（EXP-13 结论），扩容只扩读；
- **回源通道**：~100/s（qemu Router）——TTL 600s 过期风暴（每 10min）与
  Redis 冷重启（Game Day）都撞在这堵墙上；**2h 长稳证明零余量设计
  （需求 33/s ≈ 容量 24-52/s）导致相变塌陷**：T+40min 起写路径全超
  1s 预算、业务 TPS=0——这是全课程最重要的否定结论；
- **过载行为**：900 rps 有效吞吐封顶 ~820/s，1.7% 明确拒绝（429/503/504）；
- **剩余容量**：热缓存下 1 api + 1 router 仍扛 600 rps（0.19% 失败）。

## 4. 只在本地模拟成立的结论（结论边界）

1. **HA 模拟档**：3 个 MySQL 成员/KRaft 成员同宿主机、同存储——验证了
   软件故障转移语义（选主/拒写/多数派），**不能证明宿主机级 HA**；
2. **qemu Router**：所有 HA 档延迟/容量数字都含模拟放大，绝对值不可
   外推（arm64 原生 Router 会显著不同）；
3. **Game Day 双故障**：读路径 44% 拒绝率是 10000 SKU 键空间 +
   1024 stale 上限 + 100/s 回源通道的乘积——单机边界，不是架构极限；
4. **DR**：备份在宿主机 = 「K8s 卷故障域之外」，不是异地容灾；
   Kafka 复用原集群（机房级事件需独立集群或事件归档，选做）；
5. **单机 6 核/16GB 资源预算**：所有副本数/连接池/内存 limit 都是为这台
   机器调的，换环境必须重基线（roadmap §7.2 已固化该纪律）。

## 5. 故障教训 Top 8（跨实验）

1. **零余量的缓存设计是延迟引爆的无缓存**（EXP-19 长稳）：过期需求
   ≈ 回源容量时系统在一个 TTL 窗口后相变塌陷（写 TPS→0），且短测试
   结构上不可见——可持续性公式（键空间/TTL << 回源容量）必须设计期核算；
2. **资源预算要分三档**：正常态 / 故障态 / 备份态——EXP-13（扩容不破下游）、
   EXP-16（切主 OOM）、EXP-18（备份 OOM secondary）三次实证；
2. **探针误杀是隐形杀手**：liveness 在高负载下超时 → 重启级联 →
   多数派失守（EXP-10 Kafka、EXP-16 MySQL、EXP-19 会话间隙的 13 次重启）；
3. **「依赖前置资源存在」的组件不能并发拉起**：Kafka consumer 先于 topic
   入组 = 0 分区分配且永不自愈（EXP-18）；
4. **共享名资源在多清单间互相覆写**（EXP-17 Service selector 惨案）；
   **kubectl apply 会重置 set env/image**（EXP-13/16）——单一事实源纪律；
5. **在单实例验证过的 SQL 到集群上要重验**（GR 的 Error 1869，EXP-16）；
6. **没验证过的备份等于没有备份**：第一次真恢复就踩了三个坑
   （镜像无工具、0 分区、全灭引导，EXP-18）；
7. **告警要验「触发-送达-恢复」全链路**：症状告警（用户视角）+
   容量告警（饱和视角）缺一不可（EXP-04 建立被全程复用）。

## 6. 明确不做/未覆盖（诚实清单）

- 真实支付/取消退款/Saga、跨服务事务（选做未做）；
- 分库分表、跨地域多活、Service Mesh、自建 K8s 控制面 HA（选做未做）；
- 物理备份（XtraBackup）与增量 binlog 归档流水线（主线用 mysqldump，
  生产规模应换）；
- 全栈节点故障（含控制面/存储）的 Game Day——单机环境无法声明；
- 一致性备份在 MGR 上 FTWRL 语义的深挖（实测可用，未做故障注入验证）；
- 一次 Game Day ≠ 全年可用性 SLO（roadmap 明示，不宣称）。

## 7. 如果重来一次

- **第一周就上对账器与账本**（EXP-03 的手工 SQL 用了 15 个实验才工具化，
  EXP-18 的 reconcile 应该更早存在）；
- **长稳要早做、常做**：2 小时长稳暴露的相变塌陷（TTL 过期需求 33/s ≈
  回源通道容量 24-52/s 的零余量 → 拥塞传导 → T+40min 起写路径全超
  预算）是 19 个实验全部短窗口测试在结构上不可能发现的——如果
  EXP-07 引入缓存时就跑一次 2h，这个设计缺陷能在 8 个实验前暴露；
- **缓存的可持续性公式要在设计时核算**：键空间/TTL（过期需求）必须
  << 回源通道容量，余量为零的缓存设计不是「有缓存」，是「延迟引爆
  的无缓存」；
- **故障演练脚本化更早**：每个实验的注入/采样/对账三件套高度同构，
  值得在第 5 个实验时抽成工具而不是第 19 个。
