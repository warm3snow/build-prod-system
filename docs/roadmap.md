# Production System Lab：19 个核心实验

> **目标**：基于 Kubernetes，从一个正确的最小订单系统出发，验证高并发、高可用、可靠消息、发布回滚和灾难恢复。
>
> **定位**：“0→1”指业务系统从零构建，不是 Go、MySQL、Kubernetes 零基础教学。本文件是待执行的课程设计，示例阈值不是已经测得的能力。
>
> **范围说明**：课程主线为 **19 个必做实验**，只保留必要验证，多方案穷举与真实支付/微服务/Saga 等明确为选做，不作为毕业前置。

## 1. 课程主线与边界

正常态缓存与故障态缓存、业务正确性与运行底座、在线切主与灾难恢复不能继续合并：这些实验的假设、风险和通过标准不同，强行合并只会减少标题。

### 1.1 必做与选做

**必做**：事务与幂等、可复现容量测量、数据库与缓存优化、可靠事件、队列反压、过载保护、HPA、Pod/Node 故障、发布回滚、MySQL/Kafka 高可用、独立恢复、综合验收。

**选做，不影响本版毕业**：

- Bloom Filter、多种限流算法、多种缓存重建策略的完整比较。
- Kafka-first 异步下单、真实支付、取消退款、跨服务 Saga/TCC。
- Redis Cluster、KEDA、自研网关、Service Mesh、分库分表、跨地域多活。
- 完整日志检索平台、复杂追踪后端、多套 CI/CD 或 GitOps 平台。
- 自建高可用 Kubernetes 控制面和可用区级故障演练。

选做内容不是隐藏的前置条件。将来若纳入必做，必须重新评估课程范围，而不是继续声称“19 个实验全部覆盖”。

## 2. 固定业务边界，避免架构失控

### 2.1 主线业务

维护一个 Flash Order 业务：商品及展示库存查询、创建订单、订单结果查询、异步订单后置任务。

- 默认每个订单只购买一个 SKU 的一个单位；课程主线不补货、不取消、不退款。
- 库存与订单保存在同一个 MySQL 事务边界内；Redis 只存可重建的查询缓存。
- 用户使用实验身份，不建设账户体系；幂等键按实验用户和操作隔离。
- 异步后置任务用通知记录或订单投影模拟，不调用真实支付、短信等外部系统。
- 模块优先放在一个 Go 应用内。仅消费者、Outbox Relay 和可控依赖模拟器按实验需要独立运行。

### 2.2 同步下单语义始终不变

**下单成功响应意味着：订单与库存变更已经提交。** 网络超时只表示客户端不知道结果，不能等同于订单失败；客户端应使用原幂等键重试或查询。

加入 Kafka 后，主线演进为：

```text
客户端 → 入口 → Order API × N
                    ├── Redis：可重建查询缓存
                    └── MySQL：库存＋订单＋幂等结果＋Outbox，同一事务
                                  │
                             Outbox Relay
                                  │
                                Kafka
                                  │
                              Consumer
                                  └── Inbox 去重＋后置业务修改，同一事务
```

图中表示逻辑职责；MySQL 高可用阶段通过 Router 连接集群。Kafka 中的订单后置任务完成时间与同步下单延迟分别测量。

**重要限制**：本版队列削峰保护的是后置处理能力，不能声称它提高了前置 MySQL 订单写入的持续容量。Kafka-first 异步下单属于选做；采用它时必须另定义“已受理”和“订单已创建”，增加结果查询、拒绝/失败终态与端到端完成 SLO。

### 2.3 全程不变量

在“单 SKU、每单一件、无补货取消”的主线模型下，按 SKU 校验：

- 剩余库存非负；初始库存＝剩余库存＋已提交订单数。
- 同一用户、同一操作、同一幂等键最多产生一个订单；相同键但不同请求参数应明确拒绝。
- 客户端已收到成功响应的订单，在约定的局部单故障模型内仍可查询。
- 加入 Outbox 后，每个已提交订单均有可追踪的订单事件；恢复并排空后，不存在无法解释的遗漏或重复副作用。
- 主线订单仅承诺创建结果，不虚构支付或履约状态。后置任务状态只允许按定义转换，终态不因重复消息倒退。

从 `EXP-03` 开始复用自动数据校验器；`EXP-09` 增加消息与副作用对账。客户端成功响应账本保存在故障目标之外，用于故障后的逐单核验。

灾难恢复可能按事前约定的 RPO 丢失最近一段数据，必须单独列出损失订单；不能套用局部故障“成功订单不丢”的口径，更不能把恢复到旧快照称为零丢失。

## 3. 环境、测量与安全约定

### 3.1 技术栈与环境分档

| 项目 | 主线选择 |
|---|---|
| 应用 | Go、REST/JSON、MySQL 驱动；模块化单体 |
| 运行底座 | Kubernetes、一个受维护的入口控制器、一套 Helm 模板或等价声明式配置 |
| 数据 | MySQL、Redis、Kafka；按实验顺序引入，不第一天部署全套 |
| 可观测性 | Prometheus、Grafana、告警接收端、结构化日志、Go `pprof`；异步阶段增加 OTel 上下文关联 |
| 压测 | k6，一套脚本扩展使用；不再同时学习多套压测工具 |
| HA 默认方案 | MySQL InnoDB Cluster 单主模式＋Router；Kafka KRaft |

开始前记录确切的软件版本、镜像标识、客户端版本、节点规格和存储类型；不以浮动 `latest` 作为复现依据。MySQL 高可用采用一套成熟方案，不自研选主，也不比较多个运维框架。[4]

| 环境 | 用途 | 可以得出的结论 |
|---|---|---|
| 日常实验档 | 单实例数据组件、按需启动监控；本地集群即可 | 功能、性能对照、进程故障与逻辑调度行为 |
| HA 模拟档 | 多个逻辑 Node、MySQL 三实例、Kafka 三 Broker/三 Controller；可共用实验宿主机 | 软件故障转移和模拟节点失效；不能证明宿主机级 HA |
| HA 实证档 | 副本跨独立宿主机，入口与 Router 不形成单实例瓶颈，备份处于目标故障域外 | 在明确列出的物理单点故障范围内验证业务可用性 |

Kafka 的 Broker 与 Controller 是不同角色，不能以“三个 Broker”推断控制器已有多数派。MySQL、Kafka、副本卷和备份的放置也必须出现在拓扑图中。

如果只有一台电脑，可以完成 HA 模拟档，但最终报告必须标注物理故障域限制。若要声称宿主机级 HA，需要 HA 实证档；不要求为了课程立即购买云资源。

维护一张组件清单：副本数、CPU/内存请求与限制、磁盘预算、存储故障域、所在节点、重建方式。每次只启用当前阶段必需组件。控制面/etcd、DNS、入口、存储的单点要列入边界；未测试项不写“已高可用”。

### 3.2 固定压测口径

`EXP-01` 定义业务目标，`EXP-04` 建立实测基线。设备能力不足时可以事前登记“缩尺实验档”，但不得通过事后降低阈值把失败改成成功。

建议的初始负载档：80% 商品/展示库存查询、10% 下单、10% 订单查询。配套固定数据种子、数据规模、库存准备、请求体大小、热点分布、连接复用和缓存冷热状态。

| 口径 | 课程约定 |
|---|---|
| 到达率 | 区分目标到达率、实际发出的请求和实际成功业务量 |
| k6 模型 | 固定到达率场景使用开放模型，记录 `dropped_iterations`、VU 使用及压测机 CPU/网络；多请求迭代不能直接把迭代率当 QPS [3] |
| 错误分类 | 系统错误、库存不足、限流拒绝、幂等重放分别计数；不通过排除所有非 2xx 美化可用性 |
| 正常态工况 | 库存充足，避免用库存耗尽后的快速拒绝代替订单吞吐 |
| 对照窗口 | 建议预热 2 分钟、稳定测量至少 15 分钟；主要 Before/After 重复 3 次，报告波动 |
| 长稳 | 毕业前做至少一次 2 小时测试；长稳期间资源/队列不能无解释地持续增长 |
| 容量 | 同时报告符合 SLO 的持续容量、突发流量承受时长、失去一个故障单元后的容量 |
| 故障观察 | 单独展示故障前、故障中、恢复后时序；不能用全程平均值稀释中断 |

可采用以下**教学初值**，随后在每个实验开始前冻结该实验使用的数值：

- 正常态商品查询 P99 ≤ 200ms，下单 P99 ≤ 500ms，系统错误率 ≤ 0.1%。
- 正常态后置任务完成延迟 P99 ≤ 5s；突发流量下另设最长积压年龄和排空时限。
- 目标 QPS/TPS、允许限流比例、故障窗口可用性、受影响订单数、HA 恢复时间、DR 恢复时间和 RPO，必须结合环境在实验表中填写，不留 X/Y/Z。
- SLO 区分正常态、超载态和故障态；定义统计窗口、分母和观察粒度。内部实验主要使用 SLI/SLO，不把 SLA 当成没有测量定义的口号。

数据正确性不能因设备性能差而放宽。性能优化未成立可以形成有效的否定结论，但缺失必做能力或违反正确性不能算通过。

### 3.3 故障与恢复安全边界

- 只针对独立实验环境、实验 Namespace 和合成数据操作，不连接真实业务数据。
- 故障开始前填写目标、影响范围、持续时间、停止阈值、撤销方式、恢复负责人和备份位置。
- 确保注入器、计时器、压测结果和成功响应账本不随目标一起丢失。
- 单故障脚本先验证能够撤销；综合演练最多叠加已单独验收过的故障。
- 发现库存/订单不变量破坏、磁盘接近事前停止水位、监控失联或影响超出实验范围，立即停止新增流量与故障，保留证据后恢复。
- 灾备通过“隔离原环境＋恢复到新环境”验证，不以直接销毁唯一副本作为学习前提。

## 5. 19 个实验的最小执行设计

### EXP-01：业务契约、容量模型与实验边界

**前置**：具备 Go、SQL、HTTP、容器和 Kubernetes 基础；无需已有业务代码。

**核心假设**：只有把业务完成标准、负载和故障范围写清楚，后面的“高并发、高可用”才可验证。

**必做**：

1. 明确第 2 节业务边界、接口成功/失败语义、幂等键作用域与数据不变量。
2. 建模请求组合、访问频次、峰值系数、热点和数据规模。DAU 本身不能唯一推导 QPS；在线人数也不等于在途请求数。
3. 定义正常态/故障态 SLI、SLO、统计窗口、RTO/RPO 目标和第一版资源预算。
4. 绘制最小架构与单点清单；区分课程最终业务目标和当前实验机的缩尺负载。

**通过标准**：评审者能从工况表判断任一次测试应使用什么流量、什么通过条件、哪些故障不在保障范围；业务正确性有可编程断言。

**交付证据**：一份业务与容量契约、一张故障域图、一张可填写为具体数值的实验参数表。本实验以建模和评审验收，不强行做压测或故障注入。

### EXP-02：Kubernetes 最小订单运行底座

**前置**：EXP-01。

**核心假设**：使用声明式配置、持久化和正确的生命周期处理，可以重复运行最小系统，而不依赖人工补环境。

**必做**：

1. 部署入口、单副本 Go 应用和单实例 MySQL；数据库使用持久卷。只实现最小商品/订单接口，库存与订单写入从一开始就使用本地事务。
2. 配置服务发现、资源请求/限制、启动/就绪/存活检查、基本超时与优雅退出。存活检查不因一个下游暂时失败而重启全部应用；Redis 等非关键依赖不作为无条件摘流依据。
3. 接入结构化日志、请求关联 ID 和基础指标端点，为 EXP-04 采集做准备。
4. 使用专用最小权限身份、非特权应用容器；不提交明文密钥，不公开数据库、指标管理面和 `pprof`。如采用 NetworkPolicy，核实 CNI 支持并做一次负向连通性检查。

**通过标准**：依据同一份配置可以在干净的实验 Namespace 重建；应用就绪前不接业务流量；重启后数据仍在；初始化过程可重复。此时不宣称数据组件已高可用。

**交付证据**：部署配置、版本/资源清单、冒烟测试、生命周期日志、最小安全检查结果。

### EXP-03：事务、并发库存与请求幂等

**前置**：EXP-02；在任何正式性能优化前完成。

**核心假设**：数据库条件更新、本地事务和持久化幂等约束能够保护完整订单写路径，而不只是保护库存字段。

**必做**：

1. 将库存扣减、订单创建、幂等结果放在同一事务中；幂等键绑定用户、操作和请求参数，不能仅依赖 Redis 锁或进程内锁。
2. 用库存 100、超过库存数量的并发请求验证；再并发提交同一幂等键，检查相同结果及参数冲突拒绝。
3. 分别注入事务中途失败、事务提交后响应丢失，使用原键重试。记录热点库存行锁等待和事务持续时间；网络调用不得放在持锁事务中。
4. 实现数据库对账器及客户端成功响应账本；将故意错误实现隔离为实验对照，不能留在主线默认路径。

**通过标准**：重复执行后库存守恒、无重复订单、无孤立扣库存；已成功响应的订单可查；响应未知的请求能通过重试/查询收敛。明确幂等记录保留期，课程内不得早于最大重试/重放窗口清理。

**交付证据**：并发/崩溃测试、唯一约束与事务边界说明、对账结果、锁等待证据。

### EXP-04：最小可观测性与容量 Baseline

**前置**：EXP-03；数据正确性测试全部通过。

**核心假设**：固定资源和负载模型后，能重复测到稳定容量，并用证据解释首要瓶颈。

**必做**：

1. 采集 HTTP RED、Pod CPU/内存/重启/CPU 节流、DB 查询与连接/等待指标；面板同时显示成功订单量、业务拒绝与系统错误。
2. 用统一 k6 脚本完成冒烟、正常负载和逐步上探；记录目标与实际到达率、P95/P99、错误分类和压测机状态。
3. 在满足 SLO 的持续负载区间重复测量，确定初始容量和首要瓶颈。保存原始结果，不只留截图。
4. 建立一条用户症状告警和一条容量告警，验证告警送达到实验接收端、故障解除后恢复通知。

**通过标准**：同一工况的结果可重复并解释波动；知道当前容量上限、瓶颈和单点；告警能触发与恢复。没有实际施加足够负载时，结论必须是“未测到上限”。

**交付证据**：负载工况、基线报告、看板配置、告警事件和数据校验结果。后续每个实验复用这一套工具，新增组件时补对应指标。

### EXP-05：Go 热点与容器资源约束

**前置**：EXP-04。

**核心假设**：修复经 Profile 证实的热点，比没有测量依据的代码重写更有效。

**必做**：

1. 在固定数据和资源下选择一个 CPU 或分配热点，用 `pprof` 获取证据；如果使用人为放大热点，必须标注实验开关与适用范围。
2. 只修改该热点，例如减少无用序列化或分配，再按同一工况重复对照。
3. 同时观察 CPU 节流、GC、内存和 goroutine，区分代码问题与容器资源限制。

**通过标准**：能够用 Profile 与压测解释收益或否定假设；资源/输入相同，正确性无回归，延迟改善不能以隐藏错误或失控内存换取。

**交付证据**：优化前后 Profile、代码差异、重复测量与资源代价。不要求遍历所有 Go 性能技巧。

### EXP-06：MySQL 查询、索引与连接预算

**前置**：EXP-04、EXP-05；复用 EXP-03 的事务及锁等待结果。

**核心假设**：合适的访问路径和有界数据库并发，比简单增大连接池更能提升稳定吞吐。

**必做**：

1. 固定一条真实业务慢查询，例如用户订单列表，在有代表性的数据规模上分析执行计划、扫描行数与排序。
2. 设计一个匹配该查询的索引并重新压测；观察写入开销。不把单列、联合、覆盖索引分别建成独立项目。
3. 索引变更完成后，再单独比较两个连接池配置，记录池等待、活跃连接、锁等待和事务时长，不把两个变量同时修改后混算收益。
4. 给 API、Relay、Consumer 预留数据库连接预算；明确后续扩容和发布额外副本也消耗连接。

**通过标准**：解释执行计划为何改变、系统瓶颈是否迁移；连接池有上限，池等待/锁等待可以区分；能说明为何继续加连接可能没有收益。

**交付证据**：执行计划、索引对照、连接预算表和 SLO 容量曲线。

### EXP-07：Cache Aside 与缓存一致性边界

**前置**：EXP-06。

**核心假设**：对允许有限陈旧的查询使用缓存，可以降低数据库压力，同时保持可解释的一致性边界。

**必做**：

1. 只缓存商品或展示库存查询；实际扣库存仍以 MySQL 事务结果为准，不能依据缓存库存保证下单成功。
2. 固定读写比例，对比无缓存、冷缓存、热缓存；观察命中率、DB QPS、请求 P99 和缓存资源。
3. 明确数据库更新后的缓存失效策略和 TTL，构造更新与旧值回填交错，测量陈旧读窗口；失效失败要能恢复。
4. 不存在对象采用短期负缓存；验证对象随后创建后，不会被负缓存无限遮蔽。

**通过标准**：缓存确实减少目标查询的 DB 负载；陈旧窗口符合事前约定；缓存内容错误或丢失不能破坏下单不变量。严格读后写一致的接口可以绕过缓存。

**交付证据**：冷热对照、并发读写时序、TTL/失效策略取舍。Bloom Filter、双删等方案不强制逐一实现。

### EXP-08：缓存失效与有界回源

**前置**：EXP-07；已有数据库安全容量和连接预算。

**核心假设**：缓存故障应导致受控降级，而不是把缓存流量直接转移成数据库事故。

**必做**：

1. 以“热点 Key 过期”为主要对照场景，用进程内请求合并减少重复回源；注明多副本下合并范围仅限单进程。
2. 为回源设置独立超时、并发上限和有界等待；超限时明确拒绝，或仅对允许陈旧的查询返回旧值。该最小保护在本实验实现，不等待 EXP-11。
3. 使用相同保护链路测试 Redis 不可用及恢复，观察数据库负载、核心下单能力和缓存重建突发。
4. 检查负缓存对不存在 ID 的回源效果；大量 Key 同时过期、持续 Hot Key 打满 Redis 作为选做，不穷举所有缓存故障算法。

**通过标准**：约定故障负载下 DB 并发不越过预算，降级/拒绝可观测，订单正确性保持；Redis 恢复不会引起第二次无界回源。

**交付证据**：热点和 Redis 故障时序、回源/拒绝指标、恢复对账。随机 TTL 主要缓解批量过期，不能作为单个持续热点的万能方案。

### EXP-09：Outbox、消费幂等与可靠事件

**前置**：EXP-03、EXP-04、EXP-08；加入单实例 Kafka 并记录其故障保障边界。

**核心假设**：业务事务内记录事件，配合可重试投递与事务内消费去重，可消除应用崩溃带来的双写缺口。

**必做**：

1. 在订单本地事务中写入带唯一事件 ID 的 Outbox；Relay 只在获得约定的 Kafka 确认后标记发送，未知结果允许重试。
2. Consumer 将 Inbox 去重与后置业务修改放在同一个 MySQL 事务，业务提交后再提交消费位点。主线先使用保序处理，不能越过尚未完成的消息提交位点。
3. 分别测试数据库提交后 Relay 崩溃、消息已发送但未标记、消费事务已提交但位点未提交；验证重复投递不会重复产生业务副作用。
4. 增加 Outbox 积压数/年龄、Relay 失败、Kafka Lag、重复命中和业务完成延迟指标；传递事件/请求关联 ID 与 OTel 上下文，至少能够关联 HTTP、Relay 和 Consumer 的一次完整处理。

**通过标准**：在持久化存储仍可用的应用进程故障范围内，恢复后订单事件可以排空且副作用唯一；未投递事件保留并告警；业务成功不依赖 Kafka 当时立即可达。

**交付证据**：事务边界、崩溃点测试和逐事件对账。Kafka Exactly-once 不自动覆盖外部 MySQL 修改。[1]

**范围约束**：这里不声称单 Broker 已高可用。Outbox 在课程 DR 验收结束前保留已发送记录，并设总容量预算；积压不能无限增长，EXP-10 将落实超限策略。坏消息必须有显式失败记录及可重放处理方式，不能静默跳过后宣布全部成功。

### EXP-10：后置任务削峰、消费并行与反压

**前置**：EXP-09。

**核心假设**：队列可以吸收有限时长的突发，但只有输入、处理能力和存储预算相匹配时才可持续运行。

**必做**：

1. 对后置任务施加受控突发：使用实时订单事件，或在独立数据集中回放一批有效订单事件。回放吞吐不计为真实下单 TPS。
2. 固定分区数，比较少量消费者配置，记录业务处理吞吐、DB 负载与重平衡影响；传统消费组的分区分配限制有效并行度，不盲目增加实例。
3. 为消费者设置有限工作并发/在途任务数，保证位点提交不跳过未完成任务；下游变慢时减少消费压力。
4. 为 Kafka 磁盘/保留期、最老积压、Outbox 空间设置高水位与停止条件。达到预算时降低或拒绝新的业务受理，不能仅暂停 Relay 后继续无限增加 Outbox。

**通过标准**：峰值前能估算积压与排空时间，实测可以解释偏差；超过预算时发生明确反压/拒绝而非资源耗尽；恢复后正确排空，失败任务可追踪。

**交付证据**：输入/消费曲线、队列容量表、排空计时和业务对账。

**数量示例**：从无积压开始，输入 5,000 条/秒、消费 500 条/秒，持续 60 秒，约积压 270,000 条。回落到 100 条/秒后，若消费仍稳定为 500 条/秒且无额外重试，排空约需 675 秒。正常态完成 SLO 与突发态积压 SLO 必须分开。

### EXP-11：准入控制、时间预算与安全重试

**前置**：EXP-10；已有回源/消费者并发上限及数据库预算。

**核心假设**：有界准入、端到端时间预算与有限重试能避免服务在过载或下游抖动时自我放大。

**必做**：

1. 主线选一种限流策略，例如令牌桶，并设置在途请求上限；明确单实例、入口和多副本总预算的关系。
2. 为入口、应用、DB、缓存和模拟依赖划分时间预算；从 EXP-02 的基本超时演进为总截止时间约束，超时后取消无用工作。
3. 仅对可重试错误及幂等操作启用退避、抖动、次数/总时长上限；避免客户端、网关、服务层分别重试造成乘法放大。
4. 用固定到达率施加过载和临时失败，区分成功、业务拒绝、限流拒绝与超时；测量下游调用数与重试放大率。

**通过标准**：等待队列和在途请求有界，重试受总预算限制，超载有明确反馈；缩减依赖压力的同时仍满足约定核心业务 SLO，不能只靠拒绝全部请求通过。

**交付证据**：预算表、过载曲线、重试轨迹和成功业务量。固定窗口、漏桶等算法比较为选做。

### EXP-12：熔断、资源隔离与业务降级

**前置**：EXP-11。

**核心假设**：非关键依赖可以失败而不耗尽核心订单路径的资源，但不能把核心数据校验“降级”为假成功。

**必做**：

1. 使用一个可控依赖模拟器提供非关键展示信息；不建设真实推荐或用户微服务。
2. 分别观察慢响应和持续失败对共享资源的影响，再逐项加入并发隔离与熔断，复用已有超时。
3. 验证熔断打开、半开探测、关闭的过程，限制探测并发；故障恢复时不能形成请求洪峰。
4. 定义可接受的降级结果；商品附加信息可以省略，库存事务和幂等约束不能绕过。

**通过标准**：非关键依赖故障下核心下单满足该场景 SLO；隔离池、连接与 goroutine 不失控；恢复路径可观测、可重复，降级状态不伪装成完整成功。

**交付证据**：有/无隔离对照、熔断状态、资源曲线、降级响应和核心业务校验。

### EXP-13：固定副本容量与 HPA 动态行为

**前置**：EXP-06、EXP-10、EXP-11、EXP-12。

**核心假设**：只有应用具备横向扩展收益且下游有余量时，自动扩容才有意义。

**必做**：

1. 先关闭自动扩缩容，比较 1、2、4 个副本；记录总资源和成功业务吞吐，不把增加资源的收益称为单实例优化。
2. 计算全部 API、Relay、Consumer、管理预留及发布额外副本的总连接预算；同步约束各副本的回源、限流和在途任务预算。
3. 再启用 HPA，主线只落实一种有证据支持的指标。CPU 利用率目标必须有正确的 requests 和指标来源；若瓶颈不在 CPU，说明 CPU 指标为何不适用，并选择可获得的业务指标。
4. 测量指标采集、扩容触发、调度、就绪、缓存预热的时间；测试节点资源不足的 Pending 与缩容稳定行为。

**通过标准**：分别回答“扩容有效吗”和“扩得及时吗”；最大副本数不突破下游预算；突发期保护先于新副本就绪；缩容不会丢失已提交业务或跳过未完成消息。

**交付证据**：容量曲线、单位资源成本、HPA 时序、预算与缩容结果。HPA 不自动提供新的节点资源；KEDA/节点自动扩容不是本版前置。

### EXP-14：应用 Pod/Node 故障与维护中断

**前置**：EXP-13；应用多副本且跨目标故障域放置。

**核心假设**：正确的退出、流量摘除、副本分散和剩余容量，可以使应用在约定中断下继续提供服务。

**必做**：

1. 在持续流量下区分优雅退出和进程突然中断；检查摘流、连接排空、终止宽限期与请求重试结果。
2. 做一次通过 Eviction API 的节点维护，验证 PDB；再单独做一次应用节点硬故障，验证副本分散与剩余容量。
3. 观察请求级错误、连续不可用时间、Endpoint/Pod 状态、重调度与恢复；关注 CPU 节流/OOM 等资源失效证据。
4. 验证应用入口本身不因目标节点故障成为唯一不可用路径，并复用成功响应账本核验订单。

**通过标准**：各类中断在约定 SLO 内收敛，业务不变量成立；能解释维护驱逐与硬故障机制差别。PDB 不阻止硬故障，也不约束直接删除 Pod。[2]

**范围约束**：本阶段 MySQL/Kafka 尚可能为单实例，因此只针对应用故障域，数据组件不得落在本次目标节点。EXP-16/17 完成后，EXP-19 才扩大为包含数据组件的整节点故障验收。单机多 Node 结果只标注为模拟。

**交付证据**：三类中断时序、拓扑/PDB 配置、剩余容量和逐单校验。

### EXP-15：持续流量下的发布、回滚与 Schema 兼容

**前置**：EXP-14；已有健康检查、流量摘除、业务回归和容量预算。

**核心假设**：版本变更可以在有流量和新旧版本共存时完成；失败后回滚应用不会被不兼容数据变更阻断。

**必做**：

1. 主线只采用 Kubernetes 滚动发布，配置更新策略和发布前容量余量；PDB 不能代替 Deployment 自身的滚动更新策略。
2. 在持续负载下发布正常版本，再发布一个可控坏版本；通过指标或发布门禁识别失败并回滚。
3. 用一个向后兼容的 Schema 变更验证 expand/contract 思路：先扩展结构、保持旧版本可用；破坏兼容的收缩不与本次发布捆绑。
4. 将单元/集成、幂等/库存回归、冒烟和发布后 SLO 检查组成同一条可重复发布流程；脚本即可，不强制建设 CI/CD 平台。

**通过标准**：正常发布和回滚时核心业务满足约定目标；坏版本被识别并在发布恢复预算内撤回；回滚后旧应用仍能读写现有数据。明确“镜像回滚”不等于“数据库回滚”。

**交付证据**：发布时序、新旧版本共存结果、错误版本检测、回滚计时与 Schema 兼容性测试。

### EXP-16：MySQL 在线高可用与主库切换

**前置**：EXP-15；进入 HA 档，具备至少三个 MySQL 实例的资源和故障域规划。

**核心假设**：成熟复制与选主机制、正确客户端行为和足够的剩余容量，可以在主库故障后恢复业务写入。

**必做**：

1. 主线固定 MySQL InnoDB Cluster 单主模式＋Router，记录成员、多数派、路由、持久化与一致性配置；Router 也要有可用性安排。[4]
2. 持续提交订单后中断主库，观察故障检测、选主、应用连接失效、重连和写入恢复；不能假定 Router 会透明续接中断中的事务。
3. 配置并验证切主时的一致性等待策略，防止新主尚未应用完相关事务便返回陈旧结果；记录复制积压、切换后读写行为与成功响应订单。提交结果未知时，使用原幂等键核验/重试。
4. 观察旧主重新加入，确认不会以独立可写主继续接受流量；失去多数派时优先正确拒写，不以绕过保护换取“可用”。

**通过标准**：在单成员故障且多数派/存储条件成立的约定场景中，恢复时间与数据损失符合预设目标，订单核验通过；恢复后的持续容量仍满足要求。

**交付证据**：故障转移时序、客户端错误分类、逐单核验、实测恢复时间与数据损失。备份恢复留给 EXP-18，不能拿恢复备份替代本实验。

### EXP-17：Kafka 高可用与事件完整性

**前置**：EXP-09、EXP-10、EXP-16；进入 Kafka HA 档。

**核心假设**：明确复制确认条件、控制器多数派和客户端重试边界后，才能验证 Broker 故障下的消息可靠性。

**必做**：

1. 采用三个 Broker、三个 KRaft Controller 的实验拓扑，跨声明的故障域放置；主线 Topic 复制因子为 3，生产者 `acks=all`，`min.insync.replicas=2`，不使用可能丢数据的非同步副本强行选主。
2. 持续产生订单事件，中断一个承载分区 Leader 的 Broker，记录 ISR、Leader 切换、生产失败/重试、消费 Lag 与恢复。
3. 单独验证控制器角色单点中断后的多数派条件；资源有限时角色可共用实验节点，但必须记录共同故障影响，不能只测试 Broker 进程。
4. 用事件 ID 对账 Outbox、Kafka 消费结果和副作用。确认失败或结果未知的投递不标记完成，恢复后允许重复投递并去重。

**通过标准**：在预设单点故障范围内，最终无无法解释的事件遗漏或重复业务副作用；恢复时间和积压排空符合预算。ISR 不足时明确不可用或反压，不能同时承诺任意故障下都可写且零丢失。

**交付证据**：拓扑与配置快照、ISR/控制器/生产消费时序和逐事件校验。Exactly-once 的边界仍遵守 EXP-09，不把生产者幂等当成业务幂等。[1]

### EXP-18：独立备份恢复与跨组件对账

**前置**：EXP-16、EXP-17；备份与成功响应账本位于目标故障域之外。

**核心假设**：只有在不能依赖原数据库和原卷的情况下恢复并核验业务，才能证明备份与恢复流程有效。

**必做**：

1. 记录 RTO/RPO 目标、完整备份点与持续写入的成功响应账本；主线采用可验证的一致性备份。目标 RPO 小于备份间隔时，必须加上 binlog 归档/PITR 或其他足以满足目标的机制。
2. 隔离原数据环境，在新 Namespace/新卷恢复；备份从故障域外取得，不能复用原数据卷假装恢复。
3. 恢复期间冻结入口、Relay 和 Consumer，排空或确认终止在途事务，并隔离旧写入方；确定恢复后的业务数据水位，一并核验订单、库存、幂等、Outbox、Inbox 和后置副作用表。
4. 主线以恢复后的订单与保留的 Outbox 为权威，重放范围必须覆盖已发送但未消费的记录。保留原事件 ID 与业务去重身份，在隔离 Topic/新消费组中重放，并复用恢复的 Inbox 去重。不能盲目消费恢复点之后的旧 Kafka 事件，也不能复用领先于恢复数据的消费位点而跳过任务。
5. 核验通过后按受控顺序恢复写入和后置处理；列出恢复点之后丢失的已确认订单、需补偿的派生结果及残留失败任务。

**通过标准**：无需原数据环境即可恢复核心读写；库存与订单对得上，幂等和事件重放正确；实际恢复耗时、最后可恢复数据点和逐单损失符合事前目标。

**恢复边界**：本版后置副作用与 Inbox 同库同事务、属于同一一致性恢复集。若选做真实外部调用，数据库回退不能撤销已经发生的外部副作用，必须另行验证目标端幂等或对账补偿。

**交付证据**：恢复 Runbook、备份可用性证明、RTO 计时、数据损失清单和跨组件对账。RPO 是目标，实测数据损失窗口是结果；两者分别报告。Kafka 异地复制不是本版必做。

### EXP-19：全链路长稳与受控 Game Day

**前置**：EXP-01～18 必做验收全部完成；各单故障脚本已独立证明可撤销。

**核心假设**：单项能力组合后，在明确资源、负载和故障范围内仍能维持业务正确、可观测、可恢复。

**必做**：

1. 冻结最终版本、资源、业务负载、正常/故障 SLO、恢复预算和实验范围；若从日常档迁移到 HA 档，先重新建立该环境的容量基线。
2. 复用 k6 工况完成全链路正常、压力、突发与至少一次 2 小时长稳测试。记录成功订单 TPS，而不是只报告总 HTTP QPS 或回放事件速率。
3. 验证故障后剩余容量；再选择已经通过单故障验收的两个场景做受控组合，例如 Redis 延迟叠加应用 Pod 中断。全栈节点故障需事前证明入口、数据库、Kafka 及存储放置能够覆盖该目标故障域。
4. 记录用户症状、告警、定位、缓解、恢复、数据核验全过程；复用 EXP-15 的回滚与 EXP-18 的恢复证据，不重新搭建两套流程。
5. 完成架构取舍与故障复盘：哪些组件值得保留、容量边界在哪里、哪些结论只在本地模拟成立。

**通过标准**：第 6 节全部适用条目通过，无未解释的数据不一致；未覆盖或失败项如实标记。一次 Game Day 不能证明全年可用性 SLO，也不能代表任意组合故障都可承受。

**范围约束**：组合故障必须符合事前声明的容错预算；三成员多数派集群不承诺同时失去两个成员后仍能写入。整节点故障要明确是否包含控制面与共享存储故障，未覆盖的部分不纳入高可用结论。

**交付证据**：最终架构、容量报告、Game Day 时间线、验收矩阵、恢复/回滚证据与一份复盘。

## 7. 实验产物与执行方法

### 7.1 一套模板，不制造文档负担

实验报告统一放在 `docs/experiments/`，每个实验只需覆盖：

1. **问题与假设**：一个核心问题，为什么值得改。
2. **前置与复现**：代码版本、镜像、配置、环境资源、数据种子、初始化与重置方式。
3. **通过与停止条件**：具体数值 SLO、数据断言、故障范围、撤销和恢复路径。
4. **Baseline 与变更**：固定哪些变量，改变哪个因素，是否影响业务语义。
5. **证据**：负载原始结果、指标、故障时序、数据对账及重复测量。
6. **结论与取舍**：通过/失败/假设被推翻，保留还是撤回变更，适用边界和资源代价。

只有发生重要架构选择才补 ADR，只有故障有值得复用的教训才补复盘。不要求每个小变更都写多份重复材料。

### 7.2 推荐推进方式

- 按编号推进；准备好的横向能力持续复用，不在后期重新搭建。
- 每次只实现该实验的最小必要能力，先跑正确性和冒烟，再做性能或故障对照。
- 同一实验中的多个变更分步测量，不把一次性加入缓存、扩容、索引后的收益归因于单个因素。
- 不以“上了某个组件”为完成标准；不能复现、没有恢复、无法解释结果就先不进入下一阶段。
- 每阶段冻结一份可运行配置；切换日常档与 HA 档要重新测基线，不能直接比较不同硬件上的绝对 QPS。
- 先完成 19 个核心实验，再根据实际瓶颈选择扩展主题；不预先建设整套微服务和高级平台。

**最终应能回答**：在什么资源、负载和故障范围内，系统能以什么延迟完成多少正确订单；超出边界后如何拒绝、降级、回滚和恢复。
